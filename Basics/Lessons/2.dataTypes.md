# Go Data Types — From First Principles to Production

<p><b>Goal:</b> Understand Go data types from the ground up — what a type actually means, why types exist, Go's basic types, integers, floats, booleans, strings, bytes, runes, aliases, conversions, zero values, sizes, overflow, type inference, comparability, and production-grade practices.</p>

<p><b>Important:</b> We're focusing specifically on <b>data types</b>. I'll connect them to variables because types and variables are inseparable, but we won't jump into structs, interfaces, pointers, channels, etc.</p>

---

# 1. First Principles: What Is Data?

Before understanding a **data type**, understand **data**.

A program works with values:

```text
19
3.14
"Keshav"
true
'A'
```

These values represent different kinds of information.

```text
19       → number
3.14     → decimal number
"Keshav" → text
true     → yes/no
'A'      → character/code point
```

A computer needs to know how to interpret these values.

That's where **types** come in.

---

# 2. What Is a Data Type?

A data type tells the compiler:

> **What kind of value is this, what operations make sense for it, and how that value should be handled.**

For example:

```go
age := 19
```

Go determines:

```text
age
 │
 ├── value → 19
 │
 └── type  → int
```

Another:

```go
name := "Keshav"
```

```text
name
 │
 ├── value → "Keshav"
 │
 └── type  → string
```

So a useful mental model is:

```text
                    VALUE
                      │
                      ▼
                    TYPE
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       meaning     operations   representation
```

---

# 3. Why Do Types Exist?

Imagine Go allowed this:

```go
x := 10
x = "hello"
x = true
x = 3.14
```

What exactly is `x`?

Is it:

```text
integer?
string?
boolean?
floating point?
```

The compiler would have to constantly figure out what `x` currently means.

Go instead says:

```text
A variable has a type.
```

For example:

```go
x := 10
```

means:

```text
x → int
```

Therefore:

```go
x = "hello"
```

is invalid.

This gives Go strong compile-time guarantees.

---

# 4. Static Typing

Go is **statically typed**.

That means types are determined and checked at compile time.

Example:

```go
age := 19
```

Go knows:

```text
age → int
```

Then:

```go
age = 20
```

valid.

But:

```go
age = "twenty"
```

invalid.

Why?

```text
age
 ↓
int

"twenty"
 ↓
string
```

The types don't match.

---

# 5. The Big Picture of Go Types

Go has several categories of types.

For the types we're studying now:

```text
Go Types
│
├── Boolean
│   └── bool

├── Numeric

│   ├── floating-point
│   └── complex numbers
│
├── Text

│

    ├── byte
    └── rune
```

We'll go through them one by one.

---

# 6. `bool`

The simplest type.

A boolean represents one of two states:

```text
true
false
```

Example:

```go
isLoggedIn := true
```

Type:

```text
isLoggedIn → bool
```

Another:

```go
isAdmin := false
```

---

# 7. Why Does `bool` Exist?

Many decisions in programs are binary:

```text
logged in?
yes/no

active?
yes/no

valid?
yes/no

available?
yes/no
```

A boolean represents this directly.

For example:

```go
isLoggedIn := true

if isLoggedIn {
    fmt.Println("Welcome")
}
```

The value itself represents the state.

---

# 8. Boolean Operations

You can combine booleans.

### AND

```go
a && b
```

Means:

> Both must be true.

Example:

```go
isLoggedIn := true
isAdmin := true

if isLoggedIn && isAdmin {
    fmt.Println("Admin panel")
}
```

---

### OR

```go
a || b
```

Means:

> At least one must be true.

Example:

```go
isAdmin := false
isModerator := true

if isAdmin || isModerator {
    fmt.Println("Has elevated access")
}
```

---

### NOT

```go
!a
```

Flips the boolean.

```go
active := true

fmt.Println(!active)
```

Output:

```text
false
```

---

# 9. Boolean Zero Value

The zero value of:

```go
bool
```

is:

```text
false
```

So:

```go
var isActive bool
```

means:

```text
isActive → false
```

# 10. Integer Types

Now the most important numeric family.

Go provides several integer types:

```text
int
int8
int16
int32
int64

uint
uint8
uint16
uint32
uint64
uintptr
```

Don't memorize all of them blindly.

Understand why they exist first.

---

# 11. What Is an Integer?

An integer is a whole number.

Examples:

```text
-100
-5
0
1
19
1000
```

No fractional component.

Go's default general-purpose integer type is:

```go
int
```

Example:

```go
age := 19
```

Usually:

```text
age → int
```

---

# 12. Signed Integers

Types beginning with:

```text
int
```

represent both positive and negative values.

For example:

```go
var temperature int
```

could contain:

```text
-10
0
25
40
```

The negative sign is allowed because the type is **signed**.

---

# 13. What Does `int8` Mean?

The number indicates the number of bits.

```text
int8
```

means:

```text
8 bits
```

Because 8 bits can represent:

```text
256
```

different bit patterns.

For a signed integer, the range is:

```text
-128 to 127
```

So:

```go
var x int8 = 127
```

is valid.

But:

```go
var x int8 = 128
```

is not valid as a constant assignment.

---

# 14. Integer Sizes

The basic signed integer ranges are:

```text
int8
→ -128 to 127

int16
→ -32,768 to 32,767

int32
→ approximately -2.1 billion to 2.1 billion

int64
→ approximately -9.22 quintillion to 9.22 quintillion
```

You don't need to memorize every exact boundary immediately.

Understand:

```text
more bits
   ↓
more representable values
```

---

# 15. Why Have Different Integer Sizes?

Because sometimes you care about representation size or an external format.

For example, a protocol might explicitly specify:

```text
signed 32-bit integer
```

Then `int32` communicates that requirement.

Similarly, some binary file format may define a field as exactly 16 bits.

In those cases:

```go
int16
```

is meaningful.

---

# 16. `int` Is Special

`int` doesn't have a fixed size across every architecture.

Its size is implementation-dependent.

On modern common 64-bit systems:

```text
int → 64 bits
```

On 32-bit systems:

```text
int → 32 bits
```

So:

```go
age := 19
```

normally uses:

```text
int
```

and that's generally what you want for ordinary integer calculations.

---

# 17. Production Rule: Prefer `int` for Normal Integer Work

For everyday Go code:

```go
age := 19
count := 100
index := 0
```

use:

```text
int
```

unless you have a specific reason to use a fixed-width type.

Don't write:

```go
var age int64
```

just because:

> 64 sounds bigger and therefore better.

Type choice should communicate requirements.

---

# 18. Unsigned Integers

Go also has:

```text
uint
uint8
uint16
uint32
uint64
```

The `u` means:

```text
unsigned
```

Unsigned integers don't represent negative numbers.

For example:

```go
var x uint8
```

can represent:

```text
0 to 255
```

---

# 19. Signed vs Unsigned

Think:

```text
signed

negative ← 0 → positive
```

while:

```text
unsigned

0 → positive
```

Example:

```text
int8
-128 ... 0 ... 127

uint8
0 ... 255
```

Unsigned types trade negative values for a larger positive range.

---

# 20. `uint8` and `byte`

This is important.

Go defines:

```go
byte
```

as an alias for:

```go
uint8
```

So:

```go
var b byte
```

and:

```go
var b uint8
```

represent the same underlying type.

But `byte` communicates something more meaningful in many contexts:

> This value represents raw byte data.

---

# 21. Why Is `byte` Useful?

You've already seen strings.

Go strings are sequences of bytes.

So:

```go
text := "hello"
```

can be converted to:

```go
data := []byte(text)
```

Now `data` represents individual bytes.

For ASCII text:

```text
'h' → byte
'e' → byte
'l' → byte
'l' → byte
'o' → byte
```

But remember:

**one character is not always one byte.**

That's where Unicode and `rune` come in.

---

# 22. `rune`

Go defines:

```go
rune
```

as an alias for:

```go
int32
```

But semantically, `rune` is used for:

> A Unicode code point.

Example:

```go
var r rune = 'क'
```

The type communicates:

> This integer represents a Unicode code point.

---

# 23. `byte` vs `rune`

This distinction is extremely important.

```text
byte
 ↓
8-bit value
 ↓
raw byte

rune
 ↓
32-bit value
 ↓
Unicode code point
```

Think:

```text
byte → raw data / UTF-8 unit

rune → Unicode code point
```

---

# 24. Character Literals

This:

```go
'A'
```

is not a string.

It is a **rune literal**.

For example:

```go
letter := 'A'
```

The inferred type is:

```text
rune
```

Conceptually:

```text
'A'
 ↓
Unicode code point
 ↓
rune
```

---

# 25. String vs Rune

Compare:

```go
name := "Keshav"
```

and:

```go
letter := 'K'
```

The first:

```text
"Keshav" → string
```

The second:

```text
'K' → rune
```

Notice:

```text
" "
```

uses double quotes for strings.

```text
' '
```

uses single quotes for rune literals.

---

# 26. This Is a Common Beginner Mistake

Wrong mental model:

```text
"K" = character
```

In Go:

```go
"K"
```

is a string.

While:

```go
'K'
```

is a rune.

So:

```go
name := "Keshav"
letter := 'K'
```

have different types.

---

# 27. Floating-Point Types

Go has:

```text
float32
float64
```

These represent numbers with fractional values.

Example:

```go
price := 99.99
```

By default, an untyped floating-point constant like `99.99` can be inferred as:

```text
float64
```

So:

```go
price := 99.99
```

typically gives:

```text
price → float64
```

---

# 28. `float32` vs `float64`

The number indicates the number of bits used for the floating-point representation.

```text
float32
→ 32 bits

float64
→ 64 bits
```

`float64` provides greater precision and range than `float32`.

For most general-purpose Go code involving floating-point values:

```go
price := 99.99
```

`float64` is the normal choice.

---

# 29. Floating Point Is Not Exact Decimal Arithmetic

This is a major production concept.

You might expect:

```go
0.1 + 0.2
```

to exactly equal:

```text
0.3
```

But binary floating-point representation cannot represent many decimal fractions exactly.

So you can encounter results conceptually like:

```text
0.30000000000000004
```

depending on the calculation and formatting.

This is not a Go bug.

It's a property of binary floating-point representation.

---

# 30. Don't Blindly Use `float64` for Money

For financial calculations, blindly using:

```go
float64
```

can introduce precision problems.

For example:

```go
price := 19.99
```

looks exact to us.

But its binary representation is not necessarily exact.

For money, use an approach appropriate to your domain, such as integer smallest units where practical:

```go
priceCents := 1999
```

Then:

```text
1999 cents
```

represents:

```text
$19.99
```

This avoids many floating-point representation problems.

---

# 31. Complex Numbers

Go also has:

```text
complex64
complex128
```

These represent complex numbers:

```text
a + bi
```

For example:

```go
z := complex(2, 3)
```

represents:

```text
2 + 3i
```

These are useful in mathematical/scientific applications.

You won't use them often in typical backend development, but they are part of Go's numeric type system.

---

# 32. Why Does Go Have Complex Types?

Because Go's type system isn't designed only for web development.

Programming languages can also be used for:

```text
scientific computing
signal processing
mathematics
engineering
numerical computation
```

Complex numbers are useful in those domains.

---

# 33. Strings

You've already studied strings deeply, so connect the concept here.

A string is:

```text
string
 ↓
sequence of bytes
 ↓
usually UTF-8 encoded text
```

Example:

```go
name := "Keshav"
```

Type:

```text
string
```

---

# 34. String Is Not `[]byte`

This distinction matters.

```go
name := "Keshav"
```

is:

```text
string
```

while:

```go
data := []byte(name)
```

is:

```text
[]byte
```

They are related, but they are different types.

---

# 35. String Is Not a Character Array

This:

```go
name := "Keshav"
```

doesn't mean:

```text
[K][e][s][h][a][v]
```

as individual Go characters.

A string is a sequence of bytes.

For ASCII:

```text
K → 1 byte
e → 1 byte
s → 1 byte
h → 1 byte
a → 1 byte
v → 1 byte
```

But Unicode can require multiple bytes.

---

# 36. Unicode Example

Consider:

```go
text := "क"
```

The visible character:

```text
क
```

is one Unicode code point.

But its UTF-8 encoding uses multiple bytes.

So:

```go
len(text)
```

does not necessarily mean:

> Number of visible characters.

It means:

> Number of bytes in the string.

---

# 37. The Three Concepts

When dealing with text, keep these separate:

```text
byte
 ↓
raw 8-bit unit

rune
 ↓
Unicode code point

string
 ↓
sequence of bytes
```

This distinction prevents a huge number of text-processing bugs.

---

For example:

```go
age := 19
```

gives:

Example:

# 41. String Literals

# 42. Rune Literals

# 43. Type Inference

Go can infer the type from the value.

```go
age := 19
```

→ `int`

```go
price := 99.99
```

→ `float64`

```go
name := "Keshav"
```

→ `string`

```go
active := true
```

→ `bool`

```go
letter := 'K'
```

→ `rune`

This is why:

```go
age := 19
```

is so convenient.

---

# 44. Explicit Types

You can always be explicit.

```go
var age int = 19
var price float64 = 99.99
var name string = "Keshav"
var active bool = true
```

The compiler now doesn't need to infer the variable's type from the initializer.

---

# 45. Type Conversion

Go is strict about types.

Suppose:

```go
age := 19
```

and:

```go
var price float64 = 99.99
```

You may want to convert:

```go
ageAsFloat := float64(age)
```

Now:

```text
age
 ↓
int

ageAsFloat
 ↓
float64
```

---

# 46. Conversion Syntax

The general syntax is:

```go
TargetType(value)
```

Examples:

```go
float64(19)
```

```go
int(19.9)
```

```go
int8(100)
```

```go
string(65)
```

But be careful: conversions don't always mean what beginners expect.

Especially:

```go
string(65)
```

does **not** mean:

```text
"65"
```

It means a string containing the Unicode character represented by code point 65:

```text
"A"
```

This is why understanding types matters.

---

# 47. Numeric Conversion Can Lose Information

Consider:

```go
price := 19.99

whole := int(price)
```

Now:

```text
price → 19.99
whole → 19
```

The fractional portion is lost.

Conversion doesn't magically preserve information that the target type cannot represent.

---

# 48. Narrowing Conversion

Suppose:

```go
var x int64 = 1000
```

Then:

```go
y := int8(x)
```

The target type has a much smaller range.

This can produce a value that doesn't represent the original number as you intended.

So:

```text
large type
    ↓
smaller type
    ↓
possible loss / overflow
```

Be deliberate when converting.

---

# 49. Type Conversion Is Not Type Casting in the Loose Sense

Go prefers explicit conversions.

Instead of the language silently doing:

```text
int → float64
```

you explicitly write:

```go
float64(age)
```

This makes conversions visible in the code.

That's good for readability and correctness.

---

# 50. Untyped Constants

Now one of Go's more interesting type concepts.

Consider:

```go
const x = 10
```

The constant `10` can remain **untyped** until a context gives it a type.

For example:

```go
const x = 10

var a int = x
var b int64 = x
var c float64 = x
```

The constant can represent these values appropriately because constants have special compile-time behavior.

This is different from ordinary variables.

---

# 51. Untyped Constants vs Variables

Consider:

```go
x := 10
```

Now `x` is a typed variable:

```text
x → int
```

But:

```go
const x = 10
```

has an untyped constant value until context requires a type.

This is one of the reasons Go constants are powerful.

---

# 52. Why This Matters

Consider:

```go
const max = 100
```

You can use it in different compatible contexts.

But:

```go
max := 100
```

creates an `int` variable.

The variable has a concrete type.

---

# 53. Type Aliases

Go allows type aliases.

For example:

```go
type MyInt = int
```

Now:

```text
MyInt
  │
  └── alias for int
```

So:

```go
var x MyInt = 10
var y int = x
```

works because `MyInt` is literally an alias for `int`.

---

# 54. Don't Confuse Alias With a New Type

This is important.

An alias:

```go
type MyInt = int
```

means:

```text
MyInt == int
```

as far as the type system is concerned.

But a defined type:

```go
type MyInt int
```

creates a **new distinct type** based on `int`.

For now, remember:

```text
= 
→ alias

no =
→ new defined type
```

We won't go deeper into custom types yet.

---

# 55. Type Size

Types have sizes.

For example:

```text
int8   → 8 bits
int16  → 16 bits
int32  → 32 bits
int64  → 64 bits

float32 → 32 bits
float64 → 64 bits
```

A bit is:

```text
0 or 1
```

So:

```text
8 bits
```

gives:

```text
2⁸ = 256
```

possible bit patterns.

---

# 56. Bits vs Bytes

Remember:

```text
1 byte = 8 bits
```

So:

```text
int8
```

uses:

```text
8 bits = 1 byte
```

while:

```text
int64
```

uses:

```text
64 bits = 8 bytes
```

This matters when memory layout and binary data become important.

---

# 57. Why Does More Bits Give a Larger Range?

Each bit can be:

```text
0
```

or:

```text
1
```

With:

```text
1 bit
```

you get:

```text
2 possibilities
```

With:

```text
2 bits
```

you get:

```text
4 possibilities
```

With:

```text
8 bits
```

you get:

```text
256 possibilities
```

In general:

```text
n bits → 2ⁿ possible bit patterns
```

That's the fundamental reason integer sizes work this way.

---

# 58. Signed Integer Range

For an N-bit signed integer:

```text
-2^(N-1)
to
2^(N-1)-1
```

For `int8`:

```text
-2⁷
to
2⁷ - 1
```

which is:

```text
-128 to 127
```

---

# 59. Unsigned Integer Range

For an N-bit unsigned integer:

```text
0
to
2ᴺ - 1
```

For `uint8`:

```text
0 to 255
```

because:

```text
2⁸ - 1 = 255
```

---

# 60. Integer Overflow

Suppose you have a small integer type:

```go
var x uint8 = 255
```

The maximum is:

```text
255
```

Adding one exceeds the representable range.

With runtime values, arithmetic on fixed-width integer types can wrap around.

Conceptually:

```text
255
 ↓
+1
 ↓
0
```

because only 8 bits are available.

This is why choosing the correct type matters.

---

# 61. Don't Use Tiny Types Without a Reason

You might think:

> My number is small, so I'll use `int8`.

For ordinary application code, that's usually unnecessary.

Prefer:

```go
age := 19
```

rather than:

```go
var age int8 = 19
```

unless `int8` has a real semantic or representation reason.

The goal isn't:

> Use the smallest type possible.

The goal is:

> Use the type that correctly communicates and supports the data.

---

# 62. `int` vs `int64`

Use `int` for general-purpose integers:

```go
count := 100
index := 0
age := 19
```

Use a fixed-width type such as:

```go
int64
```

when the domain or external representation specifically requires it.

For example:

```text
database field
binary protocol
file format
cryptographic/numeric API
```

that explicitly requires 64-bit integers.

---

# 63. Don't Confuse `int` With `int32`

These are distinct types.

```go
var a int = 10
var b int32 = 20
```

You cannot freely mix them:

```go
a + b
```

is invalid without an appropriate conversion.

You need:

```go
a + int(b)
```

or:

```go
int32(a) + b
```

depending on what the operation should mean.

---

# 64. Why Is Go Strict About This?

Because automatic conversions can hide bugs.

Imagine:

```text
int64
 ↓
int32
```

The value might not fit.

If Go silently converted everything, you could accidentally lose information.

Explicit conversion forces you to acknowledge:

> I'm intentionally converting this value.

---

# 65. Type Compatibility

Suppose:

```go
var a int = 10
var b int = 20
```

This works:

```go
a + b
```

because both have the same type.

But:

```go
var a int = 10
var b int64 = 20
```

and:

```go
a + b
```

doesn't work directly.

Why?

```text
a → int
b → int64
```

Different types.

---

# 66. A Useful Mental Model

When you see:

```go
a + b
```

ask:

```text
What is the type of a?
What is the type of b?
Is this operation valid between those types?
```

Don't just look at the values.

Look at their **types**.

---

```text
bool

```

```text
integer types

```

```text
floating-point types
→ 0
```

```text
→ ""
```

For example:

```go
var age int
var price float64
var active bool
var name string
```

gives:

```text
age    → 0
price  → 0
active → false
name   → ""
```

---

# 68. Zero Value Is One of Go's Superpowers

Go tries to make zero values useful.

Example:

```go
var count int

count++
count++
```

Now:

```text
count → 2
```

You didn't need:

```go
count := 0
```

The zero value already gave you `0`.

---

# 69. Strings Have a Useful Zero Value

```go
var name string
```

gives:

```text
name → ""
```

You can safely compare:

```go
if name == "" {
    fmt.Println("No name")
}
```

This is common Go code.

---

# 70. Booleans Have a Useful Zero Value

```go
var isActive bool
```

gives:

```text
false
```

So:

```go
if isActive {
    ...
}
```

doesn't execute until the variable becomes true.

---

# 71. Type Determines Zero Value

Think:

```text
             TYPE
               │
               ▼
          ZERO VALUE
```

Examples:

```text
int
 ↓
0

bool
 ↓
false

string
 ↓
""
```

This is why understanding types also means understanding default state.

---

# 72. `byte` and `rune` Are Aliases

Remember:

```text
byte = uint8
rune = int32
```

But don't just memorize this mechanically.

The names communicate intent.

```go
b := byte(65)
```

communicates:

> This is byte-oriented data.

While:

```go
r := rune('क')
```

communicates:

> This is a Unicode code point.

The underlying representation is only part of the story.

---

# 73. Strings, Bytes, and Runes

A useful picture:

```text
                  STRING
                    │
                    │ UTF-8 encoded
                    ▼
              ┌─────────────┐
              │   BYTES     │
              └──────┬──────┘
                     │
                     │ decode
                     ▼
              ┌─────────────┐
              │    RUNES    │
              │   Unicode   │
              │ code points │
              └─────────────┘
```

So:

```text
string → bytes → decode → runes
```

This is why:

```go
len("क")
```

and:

```go
len([]rune("क"))
```

can produce different results.

---

# 74. Type Determines What `len` Means

For a string:

```go
len("hello")
```

means:

```text
number of bytes
```

For a slice:

```go
len(slice)
```

means:

```text
number of elements
```

The operation's meaning depends on the type.

That's an important programming principle:

> The same operation can have type-specific behavior.

---

# 75. Data Type vs Value

Don't confuse:

```text
type
```

with:

```text
value
```

For:

```go
age := 19
```

we have:

```text
type  → int
value → 19
```

If:

```go
age = 20
```

the value changes:

```text
type  → int
value → 20
```

The type stays the same.

---

# 76. Type Is More Stable Than Value

Think:

```text
age
 │
 ├── type → int   ← fixed
 │
 └── value → 19   ← can change
```

Then:

```text
age
 │
 ├── type → int
 │
 └── value → 20
```

The variable's value changes.

Its type doesn't.

---

# 77. Type Conversion vs Reassignment

These are completely different.

### Reassignment

```go
age := 19
age = 20
```

Same type:

```text
int → int
```

### Conversion

```go
age := 19
price := float64(age)
```

Now:

```text
int → float64
```

and a new value is produced with another type.

# 79. Which Types Should You Actually Use Often?

For normal Go development, you'll frequently encounter:

```text
int
string
bool
float64
byte
rune
```

And fixed-width numeric types when a specific representation is required:

```text
int32
int64
uint32
uint64
```

Don't force yourself to use every type just because Go provides it.

# 80. Production Rule: Choose Types Based on Meaning

Don't ask:

> Which type is smallest?

Ask:

> What does this data represent?

Examples:

```text
age
→ int

count
→ int

username
→ string

enabled
→ bool

Unicode code point
→ rune

raw byte
→ byte
```

This produces code that communicates intent.

---

# 81. Production Rule: Don't Use `string` for Everything

Bad design:

```go
age := "19"
active := "true"
score := "90"
```

Now your program has to interpret strings.

Better:

```go
age := 19
active := true
score := 90
```

Use the type that represents the actual data.

---

# 82. Why Strong Types Help

Suppose:

```go
age := 19
```

Now the compiler knows it's numeric.

You can:

```go
age + 1
```

But you cannot accidentally:

```go
age + "years"
```

The compiler stops you.

Strong typing moves many bugs from:

```text
runtime
```

to:

```text
compile time
```

which is generally much easier to deal with.

---

# 83. Production Rule: Don't Abuse `interface{}`

You may eventually encounter:

```go
interface{}
```

or:

```go
any
```

which can hold values of many types.

But don't use "anything" when you know the actual type.

Prefer:

```go
age int
```

over something that can contain arbitrary values.

Strong types give you better compiler guarantees and clearer code.

We'll study `any` and interfaces separately later.

---

# 84. Production Rule: Be Careful With Numeric Conversions

Whenever you write:

```go
int(x)
```

ask:

```text
Can information be lost?
Can the value exceed the target range?
Is this conversion intentional?
```

Especially when converting:

```text
large integer → small integer
float → integer
signed → unsigned
```

---

# 85. Production Rule: Money Needs Special Care

Avoid casually doing financial calculations like:

```go
total := 0.1 + 0.2
```

and assuming floating-point equality will always behave like decimal arithmetic.

For many applications, representing money in the smallest unit:

```go
priceCents := 1999
```

is safer.

The exact approach depends on the financial domain and requirements.

---

# 86. Production Rule: Use `float64` for Normal Floating-Point Work

For ordinary measurements:

```go
temperature := 36.5
distance := 12.75
```

`float64` is usually the natural choice.

Don't automatically choose `float32` because:

> It uses less memory.

Unless memory layout or an external API actually requires it, the extra precision of `float64` is often more useful.

---

# 87. Production Rule: Fixed Width When the Contract Says Fixed Width

Suppose an external format says:

```text
field = unsigned 32-bit integer
```

Then:

```go
uint32
```

communicates that contract.

This is different from ordinary application counters where:

```go
int
```

is usually more natural.

---

# 88. Production Rule: Use `byte` When You Mean Bytes

Compare:

```go
var x uint8
```

with:

```go
var x byte
```

Both have the same underlying type.

But:

```go
byte
```

communicates:

> This is byte-level data.

That's valuable to the reader.

---

# 89. Production Rule: Use `rune` When You Mean Unicode Code Points

Similarly:

```go
var r rune
```

communicates:

> This integer represents a Unicode code point.

Instead of:

```go
var r int32
```

which only tells the reader the storage-oriented type.

Names and types should communicate semantics.

---

# 90. Type Errors Are Your Friend

Consider:

```go
age := 19
name := "Keshav"

fmt.Println(age + name)
```

The compiler rejects it.

That's good.

The program contains an operation that doesn't make sense.

The type system catches it before execution.

# 102. The Rules You Should Have in Muscle Memory

<b>Rule 1:</b>

A type describes what kind of value you're working with.

```go
age := 19
```

means:

```text
age → int
```

---

<b>Rule 2:</b>

Go is statically typed.

```go
age := 19
age = "hello" // invalid
```

---

<b>Rule 3:</b>

Use `int` for ordinary integer work unless you have a reason for a fixed-width type.

```go
count := 100
```

---

<b>Rule 4:</b>

Use `bool` for true/false state.

```go
isActive := true
```

---

<b>Rule 5:</b>

Use `string` for text.

```go
name := "Keshav"
```

---

<b>Rule 6:</b>

`'A'` is a rune, while `"A"` is a string.

```text
'A' → rune
"A" → string
```

---

<b>Rule 7:</b>

```text
byte → uint8
rune → int32
```

but their names communicate different meanings.

---

<b>Rule 8:</b>

Use explicit conversions when changing types.

```go
float64(age)
```

---

<b>Rule 9:</b>

Conversions can lose information.

```go
int(19.99)
```

doesn't preserve the `.99`.

---

<b>Rule 10:</b>

More bits generally mean a larger representable range.

```text
int8  → smaller range
int64 → much larger range
```

---

<b>Rule 11:</b>

Don't automatically choose the smallest type.

Choose based on the **data and its requirements**.

---

<b>Rule 12:</b>

For money, don't blindly rely on floating-point values.

---

# 103. Final Mental Model

The deepest thing to understand is this:

```text
                         VALUE
                           │
                           ▼
                          TYPE
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
          Meaning       Operations    Representation
```

When you write:

```go
age := 19
```

Go isn't just seeing:

```text
19
```

It's seeing:

```text
19
 ↓
integer value
 ↓
int
 ↓
variable named age
```

When you write:

```go
price := 99.99
```

you're saying:

```text
99.99
 ↓
floating-point value
 ↓
float64
 ↓
variable named price
```

When you write:

```go
active := true
```

you're saying:

```text
true
 ↓
boolean value
 ↓
bool
 ↓
variable named active
```

When you write:

```go
letter := 'क'
```

you're saying:

```text
'क'
 ↓
Unicode code point
 ↓
rune
 ↓
variable named letter
```

And when you write:

```go
name := "Keshav"
```

you're saying:

```text
"Keshav"
 ↓
sequence of bytes
 ↓
string
 ↓
variable named name
```

So the core idea isn't **“memorize 20 Go types.”**

It's:

> **Every value has a type, and the type gives the value meaning, defines what you can do with it, and determines how Go treats it.**
