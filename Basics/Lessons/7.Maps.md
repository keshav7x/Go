# Go Maps — From First Principles to Production

<p><b>Goal:</b> Understand Go maps from the ground up — what they are, why they exist, how they work internally, how to use every important operation, common mistakes, and production-grade practices.</p>

---

# 1. First: Why Do We Need Maps?

You already learned arrays and slices.

Suppose you want to store the age of 5 students:

```go
ages := []int{18, 19, 20, 18, 21}
```

The problem is:

**How do you know which age belongs to whom?**

You could do:

```go
names := []string{"Rahul", "Keshav", "Aman", "Rohit", "Arjun"}
ages := []int{18, 19, 20, 18, 21}
```

Now:

```text
names[0] → Rahul
ages[0]  → 18

names[1] → Keshav
ages[1]  → 19
```

But this becomes annoying.

We want something like:

```text
"Rahul"  → 18
"Keshav" → 19
"Aman"   → 20
```

That's exactly what a **map** gives us.

---

# 2. What Is a Map?

A map stores **key → value** relationships.

```text
KEY              VALUE

"Rahul"   ────→   18
"Keshav"  ────→   19
"Aman"    ────→   20
```

In Go:

```go
ages := map[string]int{
    "Rahul":  18,
    "Keshav": 19,
    "Aman":   20,
}
```

Here:

```text
map[string]int
     │      │
     │      └── value type
     └───────── key type
```

So:

```go
map[string]int
```

means:

> A map where keys are `string` and values are `int`.

---

# 3. Map Mental Model

Think of a map as a **lookup table**.

```text
             MAP

        ┌─────────────────┐
        │                 │
"Rahul" ────────────────→ 18
"Keshav" ───────────────→ 19
"Aman" ─────────────────→ 20
        │                 │
        └─────────────────┘
```

Unlike an array:

```go
users[0]
users[1]
users[2]
```

a map uses a **key**:

```go
users["rahul"]
users["keshav"]
users["aman"]
```

This is the fundamental difference.

---

# 4. Array vs Slice vs Map

You have now learned all three.

### Array

```go
ages := [3]int{18, 19, 20}
```

Access:

```go
ages[0]
```

The index identifies the value.

---

### Slice

```go
ages := []int{18, 19, 20}
```

Access:

```go
ages[0]
```

Still index based.

---

### Map

```go
ages := map[string]int{
    "Rahul":  18,
    "Keshav": 19,
}
```

Access:

```go
ages["Rahul"]
```

The key identifies the value.

---

# 5. Why Maps Exist

Imagine you have 1 million users.

You want to find:

```text
user ID = "user_92831"
```

If you stored users in a slice, you'd potentially have to check:

```text
user 1
user 2
user 3
user 4
...
user 92831
...
```

A map is designed for this kind of **key-based lookup**.

Conceptually:

```text
Key
 │
 ▼
Hash
 │
 ▼
Location
 │
 ▼
Value
```

This is the fundamental idea behind hash maps.

# 6. Creating a Map

There are several ways.

## Map literal

```go
ages := map[string]int{
    "Rahul":  18,
    "Keshav": 19,
    "Aman":   20,
}
```

This is often the cleanest when you already know the data.

---

## Empty map with `make`

```go
ages := make(map[string]int)
```

Now you have an empty map.

You can add values:

```go
ages["Rahul"] = 18
ages["Keshav"] = 19
```

---

# 7. The `make` Keyword

You've already seen `make` with slices.

For maps:

```go
m := make(map[string]int)
```

This creates an initialized map that you can write to.

```go
m["age"] = 18
```

Works.

---

# 8. The Most Important Map Trap

Look at this:

```go
var ages map[string]int
```

What is `ages`?

It is a **nil map**.

You can read from it:

```go
fmt.Println(ages["Keshav"])
```

This is okay.

But:

```go
ages["Keshav"] = 18
```

will panic.

Why?

Because the map hasn't been initialized for writing.

Use:

```go
ages := make(map[string]int)
```

instead.

---

# 9. Nil Map vs Empty Map

These are different.

### Nil map

```go
var m map[string]int
```

### Empty initialized map

```go
m := make(map[string]int)
```

Conceptually:

```text
nil map:

m
│
└── nil


empty map:

m
│
└── initialized map
```

Both have:

```go
len(m) == 0
```

But writing behaves differently.

```go
var m map[string]int

fmt.Println(len(m)) // 0
```

Reading:

```go
fmt.Println(m["hello"]) // 0
```

Writing:

```go
m["hello"] = 10
```

💥 panic.

---

# 10. Adding Values

Simple:

```go
ages := make(map[string]int)

ages["Rahul"] = 18
ages["Keshav"] = 19
ages["Aman"] = 20
```

Now:

```text
ages

"Rahul"  → 18
"Keshav" → 19
"Aman"   → 20
```

---

# 11. Reading Values

```go
fmt.Println(ages["Rahul"])
```

Output:

```text
18
```

---

# 12. What Happens If the Key Doesn't Exist?

This is extremely important.

```go
ages := map[string]int{
    "Rahul": 18,
}

fmt.Println(ages["Keshav"])
```

Output:

```text
0
```

Why?

Because the map's value type is:

```go
int
```

and the zero value of `int` is:

```text
0
```

So a missing key returns the **zero value of the value type**.

---

# 13. Zero Values

Different value types have different zero values.

```text
int      → 0
float64  → 0
string   → ""
bool     → false
```

Example:

```go
scores := map[string]int{
    "Keshav": 90,
}

fmt.Println(scores["Rahul"])
```

Result:

```text
0
```

But here's the problem.

What if Rahul actually has a score of `0`?

You can't distinguish:

```text
Rahul doesn't exist
```

from:

```text
Rahul exists and score = 0
```

This is why Go provides the **comma-ok** pattern.

---

# 14. The Comma-Ok Pattern

Instead of:

```go
score := scores["Rahul"]
```

do:

```go
score, ok := scores["Rahul"]
```

Now:

```text
score → value
ok    → whether key exists
```

Example:

```go
scores := map[string]int{
    "Keshav": 90,
}

score, ok := scores["Keshav"]

fmt.Println(score)
fmt.Println(ok)
```

Output:

```text
90
true
```

---

# 15. Missing Key

```go
score, ok := scores["Rahul"]

fmt.Println(score)
fmt.Println(ok)
```

Output:

```text
0
false
```

Now we know:

```text
score = 0
ok    = false
```

So the key doesn't exist.

---

# 16. Why `ok` Is So Important

Production code often needs to distinguish:

```text
value doesn't exist
```

from:

```text
value exists but happens to equal its zero value
```

Example:

```go
settings := map[string]bool{
    "darkMode": false,
}
```

This:

```go
enabled := settings["darkMode"]
```

returns:

```text
false
```

But is that because:

```text
darkMode = false
```

or because:

```text
darkMode doesn't exist?
```

Use:

```go
enabled, ok := settings["darkMode"]

if ok {
    fmt.Println("Setting exists:", enabled)
} else {
    fmt.Println("Setting doesn't exist")
}
```

---

# 17. Checking Whether a Key Exists

The standard pattern:

```go
value, ok := m[key]

if ok {
    // key exists
}
```

Example:

```go
ages := map[string]int{
    "Keshav": 19,
}

age, ok := ages["Keshav"]

if ok {
    fmt.Println("Age:", age)
}
```

---

# 18. Shorter Existence Check

If you don't care about the value:

```go
_, ok := ages["Keshav"]

if ok {
    fmt.Println("User exists")
}
```

`_` means:

> I don't need this value.

---

# 19. Updating a Value

Maps are mutable.

```go
ages := map[string]int{
    "Keshav": 19,
}

ages["Keshav"] = 20
```

Now:

```text
"Keshav" → 20
```

You don't need a special `update()` method.

Assignment handles both:

```go
m[key] = value
```

If the key exists:

```text
update
```

If it doesn't:

```text
insert
```

---

# 20. Insert vs Update

This:

```go
m["Keshav"] = 19
```

could mean:

```text
INSERT
```

if Keshav doesn't exist.

Or:

```text
UPDATE
```

if Keshav already exists.

Same syntax.

---

# 21. Deleting a Key

Use:

```go
delete(m, key)
```

Example:

```go
ages := map[string]int{
    "Keshav": 19,
    "Rahul":  18,
}

delete(ages, "Rahul")
```

Now:

```text
"Keshav" → 19
```

Rahul is gone.

---

# 22. Deleting a Key That Doesn't Exist

This is safe:

```go
delete(ages, "Unknown")
```

No panic.

Nothing happens.

That's useful because you don't need:

```go
if exists {
    delete(...)
}
```

just to safely delete.

You can simply:

```go
delete(ages, "Unknown")
```

# 23. Getting Map Length

Use:

```go
len(m)
```

Example:

```go
ages := map[string]int{
    "Keshav": 19,
    "Rahul":  18,
}

fmt.Println(len(ages))
```

Output:

```text
2
```

Important:

`len(map)` gives the number of **key-value pairs**.

# 24. Looping Through a Map

Use `range`.

```go
ages := map[string]int{
    "Keshav": 19,
    "Rahul":  18,
    "Aman":   20,
}

for name, age := range ages {
    fmt.Println(name, age)
}
```

Conceptually:

```text
name      age

Keshav    19
Rahul     18
Aman      20
```

---

# 25. VERY IMPORTANT: Map Order

Do **not** assume this:

```go
for key, value := range m {
    ...
}
```

will always produce the same order.

For example, you might see:

```text
Keshav 19
Rahul 18
Aman 20
```

and another run:

```text
Aman 20
Keshav 19
Rahul 18
```

Both are valid.

Go intentionally does not give you a stable iteration order for maps.

---

# 26. Why Map Order Isn't Guaranteed

A map is designed around efficient lookup:

```text
key
 ↓
hash
 ↓
bucket/location
 ↓
value
```

It isn't designed as an ordered collection.

So don't build logic like:

```go
for key := range m {
    // assuming first key is something
}
```

That's bad.

---

# 27. If You Need Order

Use a slice for the ordering.

For example:

```go
names := []string{
    "Keshav",
    "Rahul",
    "Aman",
}
```

and a map for lookup:

```go
ages := map[string]int{
    "Keshav": 19,
    "Rahul":  18,
    "Aman":   20,
}
```

Then:

```go
for _, name := range names {
    fmt.Println(name, ages[name])
}
```

Now the order comes from the slice.

---

# 28. Ignoring One Value

You can ignore the key:

```go
for _, age := range ages {
    fmt.Println(age)
}
```

Or ignore the value:

```go
for name := range ages {
    fmt.Println(name)
}
```

This is similar to what you've already learned with `range`.

---

# 29. Map Types

Maps have two types:

```go
map[K]V
```

where:

```text
K = key type
V = value type
```

Examples:

```go
map[string]int
```

```go
map[int]string
```

```go
map[string]bool
```

```go
map[int]float64
```

---

# 30. Keys Must Be Comparable

Not every Go type can be a map key.

The key must be **comparable**.

Common valid keys:

```go
string
int
float64
bool
```

For now, the easiest mental rule is:

> Your key needs to support `==` and `!=`.

For example:

```go
a == b
```

must make sense for the type.

---

# 31. Why Does a Map Need Comparable Keys?

Imagine:

```go
m[key]
```

The map needs to determine:

```text
"Is this the same key?"
```

That requires comparing keys.

Conceptually:

```text
requested key
      ↓
find matching key
      ↓
return value
```

So Go restricts map keys to types that can be compared.

---

# 32. The Most Important Internal Idea: Hashing

Now let's understand what's happening internally.

Suppose:

```go
ages["Keshav"]
```

The computer doesn't magically know where `"Keshav"` is.

Conceptually:

```text
"Keshav"
   │
   ▼
hash function
   │
   ▼
hash value
   │
   ▼
bucket
   │
   ▼
find key
   │
   ▼
value
```

This is why maps are commonly called **hash maps**.

---

# 33. What Is a Hash?

A hash function takes some data:

```text
"Keshav"
```

and produces a number.

Conceptually:

```text
hash("Keshav")
       ↓
   91827364
```

Another key:

```text
hash("Rahul")
       ↓
   19382741
```

The map uses this information to determine where to look.

You don't manually calculate the hash.

Go handles it internally.

---

# 34. Why Hashing Makes Maps Fast

Imagine searching a slice:

```go
users := []string{
    "A",
    "B",
    "C",
    "D",
    "E",
}
```

To find `"E"`:

```text
A ❌
B ❌
C ❌
D ❌
E ✅
```

Potentially many comparisons.

With a hash map:

```text
"E"
 ↓
hash
 ↓
bucket
 ↓
look there
```

It can jump toward the relevant location instead of scanning the entire collection.

That's the core reason maps are so useful.

---

# 35. Map Lookup Complexity

For normal use, map lookup is approximately:

```text
O(1) average
```

Meaning the average lookup time does not grow linearly with the number of entries.

Conceptually:

```text
10 entries      → fast
1,000 entries   → fast
1,000,000 entries → still approximately constant average lookup
```

But **O(1) does not mean literally one CPU instruction**.

There is still work happening:

```text
hash
→ locate bucket
→ inspect entries
→ compare key
→ retrieve value
```

---

# 36. O(1) Does Not Mean "Always Instant"

This is a common misunderstanding.

Map lookup:

```text
average: O(1)
```

doesn't mean:

```text
1 operation exactly
```

It means the amount of work is approximately constant **on average**.

The actual implementation has multiple operations.

---

# 37. Buckets

Conceptually, a map can be imagined as:

```text
                MAP

       ┌───────────────┐
Bucket │               │
   0   │ entries...    │
       ├───────────────┤
Bucket │               │
   1   │ entries...    │
       ├───────────────┤
Bucket │               │
   2   │ entries...    │
       ├───────────────┤
Bucket │               │
   3   │ entries...    │
       └───────────────┘
```

A key's hash helps determine which bucket to inspect.

---

# 38. Hash Collisions

Two different keys can produce locations that overlap.

For example, conceptually:

```text
hash("Keshav") → bucket 3
hash("Rahul")  → bucket 3
```

That's a **collision**.

The map implementation has mechanisms to handle this.

So:

```text
different keys
      ↓
possibly same bucket
      ↓
map compares actual keys
      ↓
find correct entry
```

You don't need to manually handle collisions.

---

# 39. Map Growth

Suppose your map starts small:

```text
small map
```

Then you add thousands of entries:

```text
entry
entry
entry
entry
...
```

Eventually the existing structure isn't ideal.

The runtime can grow the map's internal storage and reorganize entries.

Conceptually:

```text
small table
     ↓
more entries
     ↓
resize/grow
     ↓
larger table
```

This is one reason maps have internal complexity hidden from you.

---

# 40. Don't Think of a Map as an Array

This is important.

An array:

```go
[5]int
```

has a straightforward indexed layout.

```text
index:

0 → value
1 → value
2 → value
3 → value
4 → value
```

A map is conceptually more like:

```text
key
 ↓
hash
 ↓
bucket
 ↓
entry
```

So don't assume map memory layout behaves like:

```text
[key][value][key][value]...
```

The runtime manages the actual representation.

---

# 41. Map Lookup

When you write:

```go
age := ages["Keshav"]
```

conceptually:

```text

                 │
                 ▼
             hash key
                 │
                 ▼
             find bucket

                 ▼

                 │
                 ▼

                 │
```

This is the mental model you should remember.

# 50. Updating During a Loop

You can modify map values while iterating.

Example:

```go
scores := map[string]int{
    "Keshav": 10,
    "Rahul":  20,
}

for name, score := range scores {
    scores[name] = score + 10
}
```

Now the values are increased.

---

# 51. Adding During Iteration

You should be careful with logic that modifies the map while ranging over it.

For example:

```go
for key := range m {
    m["new"] = 10
}
```

Don't build application logic around assumptions about whether newly added entries will be visited during that iteration.

The iteration behavior isn't a mechanism for maintaining a predictable ordered traversal.

Keep iteration logic simple and explicit.

---

# 52. Deleting During Iteration

This is a useful pattern:

```go
for key := range m {
    if shouldDelete(key) {
        delete(m, key)
    }
}
```

Deleting entries during map iteration is supported.

For example:

```go
ages := map[string]int{
    "Keshav": 19,
    "Rahul":  17,
    "Aman":   20,
}

for name, age := range ages {
    if age < 18 {
        delete(ages, name)
    }
}
```

Now Rahul is removed.

---

# 53. Maps Are Reference-Like in Behavior

This is important when passing maps around.

Consider:

```go
func update(ages map[string]int) {
    ages["Keshav"] = 20
}
```

Then:

```go
ages := map[string]int{
    "Keshav": 19,
}

update(ages)

fmt.Println(ages["Keshav"])
```

Output:

```text
20
```

Why?

Because the function is operating on the same underlying map data.

Mental model:

```text
main
 │
 │ ages
 ▼
┌──────────────┐
│ underlying   │
│ map storage  │
└──────────────┘
       ▲
       │
       │
   update()
```

This becomes extremely important when designing functions.

---

# 54. Map Assignment

Suppose:

```go
a := map[string]int{
    "Keshav": 19,
}
```

Then:

```go
b := a
```

Now don't think:

```text
a → completely separate map
b → completely separate map
```

Think:

```text
a ─────┐
       ▼
   map storage
       ▲
       │
b ─────┘
```

So:

```go
b["Keshav"] = 20
```

and:

```go
fmt.Println(a["Keshav"])
```

will reflect the same underlying map contents.

---

# 55. This Is Different From Copying a Slice

You already learned slices have a backing array.

Maps similarly have runtime-managed underlying storage.

So assignment does **not** give you an independent deep copy of all map entries.

If you need a separate map, create one and copy entries.

---

# 56. Copying a Map

Example:

```go
original := map[string]int{
    "Keshav": 19,
    "Rahul":  18,
}

copyMap := make(map[string]int)

for key, value := range original {
    copyMap[key] = value
}
```

Now:

```text
original → separate map storage
copyMap  → separate map storage
```

Changing:

```go
copyMap["Keshav"] = 100
```

doesn't change:

```go
original["Keshav"]
```

---

# 57. Preallocating a Map

If you know approximately how many entries you're going to insert:

```go
users := make(map[string]int, 1000)
```

This tells Go approximately:

> I'm expecting around 1000 entries.

It can help reduce growth/reallocation work.

But don't obsess over this for tiny maps.

Bad:

```go
make(map[string]int, 3)
```

just because there are currently three entries.

Good:

```go
make(map[string]int, expectedSize)
```

when you genuinely know or reasonably estimate the size.

---

# 58. Map Capacity Is Not Like Slice Capacity

This is an important distinction.

With slices:

```go
len(slice)
cap(slice)
```

`cap` is directly observable.

With maps:

```go
len(m)
```

exists.

But you don't have:

```go
cap(m)
```

as a normal built-in operation.

You can provide an initial size hint:

```go
make(map[string]int, 1000)
```

but that doesn't mean:

```text
map capacity = exactly 1000
```

Think of it as a **hint**.

---

# 59. Maps and Memory

Maps have overhead.

If you have:

```go
map[string]int
```

the runtime needs to maintain:

```text
hash information
buckets
keys
values
metadata
growth information
```

So don't automatically replace every slice with a map.

Use the data structure that matches the problem.

---

# 60. When Should You Use a Map?

Use a map when the main operation is:

> Find something using a key.

Examples:

```text
userID → user information
username → account
countryCode → country
productID → price
route → handler
featureName → enabled
word → count
```

The common pattern is:

```text
KEY → VALUE
```

---

# 61. When Should You NOT Use a Map?

Don't use a map just because it's powerful.

If you need ordered data:

```go
[]string
```

may be more appropriate.

If you need fixed-size data:

```go
[10]int
```

may be appropriate.

Think about what operation your program needs.

---

# 62. Map as a Lookup Table

This is one of the most useful patterns.

Instead of:

```go
if role == "admin" {
    ...
} else if role == "editor" {
    ...
} else if role == "viewer" {
    ...
}
```

sometimes you can use a map:

```go
permissions := map[string]string{
    "admin":  "full",
    "editor": "write",
    "viewer": "read",
}
```

Then:

```go
permission, ok := permissions[role]
```

This turns:

```text
key → lookup
```

into a simple data structure.

Don't blindly replace every `if` with a map though. Use whichever expresses the logic more clearly.

---

# 63. Counting With Maps

One of the classic map patterns:

```go
words := []string{
    "go",
    "rust",
    "go",
    "java",
    "go",
}

counts := make(map[string]int)

for _, word := range words {
    counts[word]++
}
```

Result:

```text
go   → 3
rust → 1
java → 1
```

Why does this work?

Initially:

```go
counts["go"]
```

returns:

```text
0
```

Then:

```go
counts["go"]++
```

becomes:

```text
1
```

Next:

```text
2
```

Next:

```text
3
```

This is one of the most important map patterns to understand.

---

# 64. The Counter Pattern

General form:

```go
counts[key]++
```

Mental model:

```text
key doesn't exist
       ↓
zero value
       ↓
increment
       ↓
1
```

Next time:

```text
1
 ↓
increment
 ↓
2
```

This is why maps are extremely convenient for counters.

---

# 65. Example: Counting Names

```go
names := []string{
    "Keshav",
    "Rahul",
    "Keshav",
    "Aman",
    "Rahul",
    "Keshav",
}

counts := make(map[string]int)

for _, name := range names {
    counts[name]++
}

for name, count := range counts {
    fmt.Println(name, count)
}
```

Possible output:

```text
Keshav 3
Rahul 2
Aman 1
```

The exact order is not guaranteed.

# 66. Membership Set Pattern

Go doesn't have a dedicated built-in `Set` type.

A common way to represent a set is:

```go
set := map[string]bool{}
```

Then:

```go
set["go"] = true
set["rust"] = true
set["java"] = true
```

Check:

```go
if set["go"] {
    fmt.Println("Go exists")
}
```

A more explicit pattern when presence itself matters is:

```go
set := make(map[string]struct{})

set["go"] = struct{}{}
set["rust"] = struct{}{}
```

But don't rush into `struct{}` yet if you haven't learned structs. Just understand that maps can represent membership.

# 68. Common Beginner Mistake #1

### Writing to a nil map

Bad:

```go
var users map[string]int

users["Keshav"] = 19
```

This panics.

Good:

```go
users := make(map[string]int)

users["Keshav"] = 19
```

---

# 69. Common Beginner Mistake #2

Assuming missing keys cause an error:

```go
age := ages["unknown"]
```

No.

You'll get the zero value.

Use:

```go
age, ok := ages["unknown"]
```

if existence matters.

---

# 70. Common Beginner Mistake #3

Assuming map order

Bad:

```go
for key := range m {
    fmt.Println(key)
}
```

and expecting:

```text
A
B
C
```

every time.

Don't.

Map iteration order is not something your logic should depend on.

---

# 71. Common Beginner Mistake #4

Using a map when you need ordering

If your data needs:

```text
1st
2nd
3rd
4th
```

a map isn't naturally the right abstraction.

Use a slice when order matters.

---

# 72. Common Beginner Mistake #5

Thinking `map` is a normal value container

Remember:

```go
a := m
```

doesn't create an independent deep copy.

If you mutate `a`, you're mutating the same underlying map data.

---

# 73. Common Beginner Mistake #6

Checking existence incorrectly

Don't do:

```go
if m["Keshav"] != 0 {
    // exists
}
```

This is wrong if `0` is a valid value.

Use:

```go
_, ok := m["Keshav"]

if ok {
    // exists
}
```

---

# 74. Common Beginner Mistake #7

Using a map just to avoid writing `if`

Don't turn every piece of logic into a lookup table.

A map is great when your problem naturally looks like:

```text
key → value
```

If the logic is complicated, normal control flow can be clearer.

---

# 75. Production Best Practice: Name Maps Clearly

Bad:

```go
m := make(map[string]int)
```

when the meaning isn't obvious.

Better:

```go
userAges := make(map[string]int)
```

or:

```go
scores := make(map[string]int)
```

The type tells you less than the variable name does.

---

# 76. Production Best Practice: Make the Key Meaningful

Bad:

```go
m := map[string]int{
    "a": 10,
    "b": 20,
}
```

if `"a"` and `"b"` don't have obvious meaning.

Better:

```go
scores := map[string]int{
    "Keshav": 90,
    "Rahul":  85,
}
```

Your data structure should communicate intent.

---

# 77. Production Best Practice: Initialize Where Appropriate

If you're going to write:

```go
m["key"] = value
```

make sure the map is initialized.

Usually:

```go
m := make(map[string]int)
```

or:

```go
m := map[string]int{}
```

Both create an initialized empty map.

---

# 78. `make` vs Empty Literal

These are both valid:

```go
m := make(map[string]int)
```

and:

```go
m := map[string]int{}
```

Both produce an initialized empty map.

Use whichever makes your intent clearer.

---

# 79. Production Best Practice: Don't Rely on Zero Values Blindly

This:

```go
value := m[key]
```

is perfectly fine when:

```text
missing key → zero value
```

is exactly what you want.

For example:

```go
counts[word]++
```

is excellent.

But if existence matters:

```go
value, ok := m[key]
```

is the right pattern.

---

# 80. Production Best Practice: Keep Map Responsibilities Clear

A map should have a clear purpose.

For example:

```go
userAges
```

means:

```text
username → age
```

Don't create giant maps where every key means something different.

Good data structures make code easier to understand.

---

# 81. Production Best Practice: Don't Assume O(1) Means Free

Even though map lookup is approximately O(1) average:

```go
value := m[key]
```

still has:

```text
hashing
bucket lookup
key comparison
memory access
```

Maps can have memory overhead and cache behavior considerations.

For normal application code, don't prematurely optimize.

First choose the correct data structure.

---

# 82. Production Best Practice: Preallocate When You Know the Scale

If you're about to create a large map:

```go
users := make(map[string]int, 100000)
```

and you genuinely know you'll insert around 100k entries, the size hint can help the runtime plan storage.

But don't randomly add huge numbers:

```go
make(map[string]int, 999999999)
```

That's not optimization.

That's potentially wasteful.

# 83. Map Keys and Values Can Have Different Types

For example:

```go
prices := map[string]float64{
    "laptop":  75000,
    "keyboard": 3000,
}
```

Here:

```text
key   = string
value = float64
```

# 84. Nested Maps

Maps can contain maps.

For example:

```go
users := map[string]map[string]string{
    "keshav": {
        "city": "Guwahati",
    },
}
```

Then:

```go
fmt.Println(users["keshav"]["city"])
```

This is valid.

But don't overuse nested maps. Once data becomes complex, other data structures become useful.

For now, just understand that map values can themselves be maps.

# 85. Map of Slices

You can also have:

```go
friends := map[string][]string{
    "Keshav": {"Rahul", "Aman"},
    "Rahul":  {"Keshav"},
}
```

Then:

```go
fmt.Println(friends["Keshav"])
```

Output:

```text
[Rahul Aman]
```

This is a very useful pattern:

```text
key → collection
```

# 86. A Powerful Pattern: Grouping

Suppose:

```go
names := []string{
    "Keshav",
    "Rahul",
    "Aman",
}
```

You can conceptually build:

```text
first letter → names

K → [Keshav]
R → [Rahul]
A → [Aman]
```

Using:

```go
groups := make(map[string][]string)
```

Then append values to the appropriate key.

This is a common real-world use of maps.

# 87. Map Lookup vs Slice Search

Suppose:

```go
users := []string{
    "Keshav",
    "Rahul",
    "Aman",
}
```

Searching:

```go
for _, user := range users {
    if user == "Rahul" {
        // found
    }
}
```

This is a linear search:

```text
O(n)
```

A map:

```go
users := map[string]bool{
    "Keshav": true,
    "Rahul":  true,
    "Aman":   true,
}
```

can provide approximately:

```text
O(1) average lookup
```

So if you repeatedly ask:

> Does this key exist?

a map can be a much better fit.

This is more important than memorizing definitions.

Ask:

If:

```text
I need position
```

think:

```text

```

If:

```text
I need key-based lookup
```

think:

```text
map
```

If:

```text
I need order
```

think:

```text
slice
```

# 89. Map Mental Model

Burn this into your head:

```text
                 MAP

              key
               │
               ▼
             hash
               │
               ▼
            bucket
               │
               ▼
         matching key
               │
               ▼

```

# 90. One Complete Example

```go
package main

import "fmt"

func main() {
    ages := map[string]int{
        "Keshav": 19,
        "Rahul":  18,
        "Aman":   20,
    }

    fmt.Println(ages["Keshav"])

    ages["Keshav"] = 20

    age, ok := ages["Rahul"]

    if ok {
        fmt.Println("Rahul's age:", age)
    }

    delete(ages, "Aman")

    for name, age := range ages {
        fmt.Println(name, age)
    }
}
```

Notice how many map operations you've now used:

```text
create
↓
read
↓
update
↓
check existence
↓
delete
↓
iterate
```

# 99. The Rules You Should Remember

<b>Rule 1:</b>

```go
map[K]V
```

means:

```text
key → value
```

<b>Rule 2:</b>

```go
m[key]
```

performs a lookup.

<b>Rule 3:</b>

```go
m[key] = value
```

inserts or updates.

<b>Rule 4:</b>

```go
delete(m, key)
```

removes an entry.

<b>Rule 5:</b>

```go
len(m)
```

returns the number of entries.

<b>Rule 6:</b>

```go
value, ok := m[key]
```

lets you distinguish:

```text
exists
vs
doesn't exist
```

<b>Rule 7:</b>

```go
var m map[string]int
```

creates a nil map. You cannot write to it.

<b>Rule 8:</b>

```go
m := make(map[string]int)
```

creates a writable map.

<b>Rule 9:</b>

**Map iteration order is not guaranteed.**

<b>Rule 10:</b>

Maps are primarily for:

```text
KEY → VALUE
```

lookup.

# 100. Final Mental Model

Don't memorize:

> “Map is a hash table.”

Understand this:

```text
                  YOU
                   │
                   │
             m["Keshav"]
                   │
                   ▼
            ┌─────────────┐
            │    HASH     │
            └──────┬──────┘
                   │
                   ▼
             ┌───────────┐
             │  BUCKET   │
             └─────┬─────┘
                   │
                   ▼
             ┌───────────┐
             │ FIND KEY  │
             │ "Keshav"  │
             └─────┬─────┘
                   │
                   ▼
             ┌───────────┐
             │   VALUE   │
             │    19     │
             └───────────┘
```

And the Go API you should have in muscle memory is:

```go
m := make(map[string]int)

m["Keshav"] = 19

age := m["Keshav"]

```
