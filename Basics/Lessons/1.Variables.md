# Go Variables — From First Principles to Production

<p><b>Goal:</b> Understand Go variables from the ground up — what a variable actually is, why variables exist, how declaration works, zero values, initialization, type inference, scope, shadowing, constants, memory mental models, best practices, common mistakes, and production-grade exercises.</p>

<p><b>Important:</b> We’ll stay focused on <b>variables</b>. No structs, maps, pointers, interfaces, goroutines, etc.</p>

---

# 1. What Is a Variable?

Let's start before Go.

A program needs to work with data.

For example:

```text
age = 19
name = "Keshav"
isLearning = true
```

We need somewhere to keep these values while the program runs.

A **variable** is a named piece of program state whose value can change.

In Go:

```go
age := 19
```

You can think:

```text
age
 │
 ▼
19
```

Later:

```go
age = 20
```

Now:

```text
age
 │
 ▼
20
```

That's the fundamental idea.

---

# 2. Why Do Variables Exist?

Imagine writing:

```go
fmt.Println(19)
fmt.Println(19)
fmt.Println(19)
```

The value is just sitting there.

But if the value has meaning:

```go
age := 19

fmt.Println(age)
fmt.Println(age)
fmt.Println(age)
```

Now your program is saying:

> This `19` represents an age.

The variable gives **meaning and identity** to data.

---

# 3. Variable = Name + Type + Value

A useful mental model:

```text
        variable

      ┌───────────┐
      │   name    │
      ├───────────┤
      │   type    │
      ├───────────┤
      │   value   │
      └───────────┘
```

For:

```go
age := 19
```

conceptually:

```text
name  → age
type  → int
value → 19
```

The type is inferred by Go.

---

# 4. The Simplest Variable

```go
age := 19
```

This does several things:

```text
create variable
      ↓
name = age
      ↓
infer type
      ↓
type = int
      ↓
store value
      ↓
value = 19
```

So:

```go
age := 19
```

is approximately saying:

> Create a variable named `age`, infer its type from `19`, and store `19` in it.

---

# 5. Variables Can Change

That's why they're called **variables**.

```go
age := 19

age = 20
age = 21
age = 22
```

The same variable:

```text
age
 ↓
19
 ↓
20
 ↓
21
 ↓
22
```

At any particular point in execution, it has its current value.

---

# 6. Declaration vs Assignment

This distinction is important.

Consider:

```go
age := 19
```

This **declares** a new variable and gives it a value.

Then:

```go
age = 20
```

doesn't create another variable.

It **assigns** a new value to the existing variable.

Think:

```text
age := 19
     ↑
 declaration + initialization


age = 20
     ↑
 assignment
```

---

# 7. Declaration

Go provides the `var` keyword for explicit variable declarations.

```go
var age int
```

This means:

```text
name → age
type → int
value → zero value
```

For an `int`, the zero value is:

```text
0
```

So:

```go
var age int

fmt.Println(age)
```

prints:

```text
0
```

---

# 8. Declaration + Initialization

You can also write:

```go
var age int = 19
```

This explicitly says:

```text
name  → age
type  → int
value → 19
```

Go already knows that `19` is an `int`, but you've explicitly specified it.

---

# 9. Type Inference

Go can infer types.

Instead of:

```go
var age int = 19
```

you can write:

```go
var age = 19
```

Go sees:

```text
19
```

and determines:

```text
age → int
```

This is called **type inference**.

---

# 10. Short Variable Declaration

Go gives you an even shorter syntax:

```go
age := 19
```

This is extremely common in Go.

The `:=` operator means:

> Declare a new variable and infer its type.

Example:

```go
name := "Keshav"
age := 19
isStudent := true
```

Go infers:

```text
name      → string
age       → int
isStudent → bool
```

---

# 11. `:=` vs `=`

This is one of the most important beginner distinctions.

### `:=`

Creates a new variable.

```go
age := 19
```

### `=`

Assigns a value to an existing variable.

```go
age = 20
```

This is wrong:

```go
age = 19
```

if `age` hasn't already been declared.

And this is wrong:

```go
age := 19
age := 20
```

in the same scope because you're trying to redeclare the same variable.

---

# 12. Think of `:=` Like This

```text
:=

NEW VARIABLE
    +
TYPE INFERENCE
    +
INITIAL VALUE
```

While:

```text
=

CHANGE EXISTING VALUE
```

This mental model will save you from a lot of errors.

---

# 13. Different Variable Types

Go is statically typed.

You can have:

```go
age := 19
```

```go
price := 99.99
```

```go
name := "Keshav"
```

```go
active := true
```

The compiler knows the type.

Conceptually:

```text
age     → int
price   → float64
name    → string
active  → bool
```

---

# 14. Static Typing

Go is **statically typed**.

That means the type of a variable is known at compile time.

For example:

```go
age := 19
```

Go determines:

```text
age → int
```

Then:

```go
age = "hello"
```

is invalid.

Why?

Because:

```text
age
 ↓
int
```

but you're trying to put:

```text
string
```

inside it.

Go doesn't allow that.

---

# 15. Why Static Typing?

Imagine:

```go
age := 19
```

Your program can reason:

```text
age is always an int
```

So operations involving `age` can be checked by the compiler.

For example:

```go
age + 1
```

makes sense.

But:

```go
age + "hello"
```

doesn't.

The compiler catches the mistake instead of allowing the program to continue with an ambiguous meaning.

---

# 16. Variables Have Types

Consider:

```go
var age int
```

The type is explicitly:

```text
int
```

Now:

```go
var name string
```

The type is:

```text
string
```

And:

```go
var active bool
```

The type is:

```text
bool
```

The type determines what values the variable can hold.

---

# 17. Zero Values

This is one of Go's most important ideas.

When you declare a variable without giving it an initial value:

```go
var age int
```

Go doesn't leave it containing random garbage.

Go gives it the type's **zero value**.

For common basic types:

```text
int      → 0
float64  → 0
string   → ""
bool     → false
```

So:

```go
var age int
var name string
var price float64
var active bool
```

conceptually:

```text
age    → 0
name   → ""
price  → 0
active → false
```

---

# 18. Why Does Go Have Zero Values?

A major Go design philosophy is:

> Variables should have useful default values.

Instead of forcing you to initialize everything manually:

```go
var age int = 0
var name string = ""
var active bool = false
```

Go allows:

```go
var age int
var name string
var active bool
```

and provides sensible zero values.

This makes declarations predictable.

---

# 19. Zero Value Is Not "Nothing"

This distinction matters.

For:

```go
var age int
```

the value isn't:

```text
undefined
```

and isn't:

```text
garbage
```

It's:

```text
0
```

Likewise:

```go
var name string
```

contains the zero value:

```text
""
```

So you can safely use many zero-valued variables immediately.

---

# 20. Explicit Type Declaration

You can write:

```go
var age int = 19
```

This is valid.

But usually:

```go
age := 19
```

is cleaner when the type is obvious.

---

# 21. When `var` Is Useful

`var` becomes particularly useful when you want a variable declared before its value is known.

Example:

```go
var age int

if something {
    age = 19
} else {
    age = 20
}
```

The variable exists first.

Then later it receives a value.

This is one reason `var` remains important even though `:=` is convenient.

---

# 22. Another `var` Example

```go
var name string

name = "Keshav"

fmt.Println(name)
```

Here:

```text
declaration
    ↓
var name string

assignment
    ↓
name = "Keshav"
```

---

# 23. Multiple Variables

You can declare several variables:

```go
var age int
var name string
var active bool
```

Or together:

```go
var (
    age    int
    name   string
    active bool
)
```

This is called a **grouped declaration**.

---

# 24. Multiple Initialization

You can also do:

```go
var age, score int = 19, 90
```

Now:

```text
age   → 19
score → 90
```

You can also use:

```go
age, score := 19, 90
```

when creating both variables.

---

# 25. Swapping Variables

Go makes swapping extremely simple.

```go
a := 10
b := 20

a, b = b, a
```

Now:

```text
a → 20
b → 10
```

You don't need a temporary variable.

You don't need:

```text
temp
```

Go supports multiple assignment directly.

---

# 26. Multiple Assignment

Consider:

```go
a, b = 10, 20
```

This assigns:

```text
a → 10
b → 20
```

The right-hand side is evaluated and then assigned.

This becomes very useful throughout Go.

---

# 27. Reassignment

Once declared:

```go
age := 19
```

you can change it:

```go
age = 20
```

Then:

```go
age = 21
```

Then:

```go
age = 22
```

But you cannot change its type:

```go
age = "twenty-two"
```

because:

```text
age → int
```

---

# 28. Variable Type Does Not Change

Suppose:

```go
name := "Keshav"
```

Go infers:

```text
name → string
```

Then:

```go
name = "Rahul"
```

valid.

Because:

```text
string → string
```

But:

```go
name = 19
```

invalid.

Because:

```text
string ← int
```

The value can change.

The variable's type cannot.

---

# 29. Scope

Now we reach one of the most important variable concepts.

**Scope** means:

> Where can this variable be accessed?

Example:

```go
func main() {
    age := 19

    fmt.Println(age)
}
```

`age` exists inside the scope where it was declared.

---

# 30. Block Scope

Consider:

```go
if true {
    age := 19
    fmt.Println(age)
}

fmt.Println(age)
```

The second `fmt.Println(age)` doesn't work.

Why?

Because `age` was declared inside the `if` block.

Visualize it:

```text
main scope
│
│
├── if block
│   │
│   └── age
│
│
└── age is NOT visible here
```

---

# 31. Variables Live Within Their Scope

Example:

```go
func main() {
    name := "Keshav"

    if true {
        age := 19

        fmt.Println(name)
        fmt.Println(age)
    }

    fmt.Println(name)
}
```

Inside the `if` block:

```text
name → accessible
age  → accessible
```

Outside:

```text
name → accessible
age  → not accessible
```

because `name` belongs to the outer scope while `age` belongs to the inner scope.

---

# 32. Inner Scope Can Access Outer Variables

Example:

```go
func main() {
    name := "Keshav"

    if true {
        fmt.Println(name)
    }
}
```

This works.

The inner scope can access variables from the outer scope.

Conceptually:

```text
outer
│
│ name
│
└── inner
     │
     └── can see name
```

---

# 33. Shadowing

This is a very important Go variable concept.

Consider:

```go
name := "Keshav"

if true {
    name := "Rahul"
    fmt.Println(name)
}

fmt.Println(name)
```

Output:

```text
Rahul
Keshav
```

Why?

Because the inner:

```go
name := "Rahul"
```

creates a **new variable** that shadows the outer variable.

Visualize:

```text
outer scope

name → "Keshav"
│
└── inner scope
     │
     name → "Rahul"
```

Inside the inner scope, the nearest `name` is used.

---

# 34. Shadowing vs Assignment

These are different:

### Shadowing

```go
name := "Keshav"

if true {
    name := "Rahul"
}
```

New variable.

### Assignment

```go
name := "Keshav"

if true {
    name = "Rahul"
}
```

Same variable.

After the `if`:

```text
name → "Rahul"
```

This distinction is **critical**.

---

# 35. Why Shadowing Can Be Dangerous

Look at:

```go
count := 10

if true {
    count := 20
    fmt.Println(count)
}

fmt.Println(count)
```

You might accidentally think:

```text
count became 20
```

But it didn't.

You created another `count`.

Result:

```text
20
10
```

So be careful with `:=`.

---

# 36. `:=` Has an Important Rule

Within a scope, `:=` must declare at least one **new variable**.

For example:

```go
name := "Keshav"
age := 19
```

Good.

But:

```go
name := "Keshav"
name := "Rahul"
```

is invalid in the same scope.

Because there is no new variable.

---

# 37. Mixed `:=`

This is valid:

```go
name := "Keshav"

name, age := "Rahul", 19
```

Why?

Because:

```text
name → already exists
age  → new
```

At least one variable is new.

So Go allows the declaration.

Now:

```text
name → "Rahul"
age  → 19
```

---

# 38. Scope Is About Visibility, Not Just Lifetime

For now, think of scope as:

> Where the name can be used in the source code.

This is extremely useful when reading programs.

If you see:

```go
x := 10
```

ask:

> From where until where can I use `x`?

That is the variable's scope.

---

# 39. Package-Level Variables

Go also allows variables outside functions.

For example:

```go
package main

import "fmt"

var appName = "MyApp"

func main() {
    fmt.Println(appName)
}
```

`appName` can be accessed by code in the appropriate package scope.

But don't make everything global just because you can.

We'll come back to production practices.

---

# 40. Local Variables

A variable declared inside a function:

```go
func main() {
    age := 19
}
```

is local to that function's scope.

Local variables are generally easier to reason about because their usage is limited.

---

# 41. Naming Variables

Good:

```go
age := 19
name := "Keshav"
score := 95
```

Bad:

```go
a := 19
x := "Keshav"
q := 95
```

unless the context makes those names obvious.

A variable name should tell you what the value represents.

---

# 42. Go Naming Style

Go generally prefers concise names.

Good:

```go
userID
userName
age
score
count
price
```

Don't write absurdly long names:

```go
theCurrentAgeOfTheUserWhoIsCurrentlyLoggedIntoTheApplication := 19
```

That's technically possible but terrible.

Prefer:

```go
userAge := 19
```

---

# 43. Short Names Can Be Good

Short names aren't automatically bad.

For a small loop:

```go
for i := 0; i < 10; i++ {
    fmt.Println(i)
}
```

`i` is perfectly understandable.

Similarly:

```go
for _, v := range values {
    fmt.Println(v)
}
```

can be reasonable when the context is obvious.

The rule is:

> Name variables according to how much meaning the variable needs to communicate.

---

# 44. Boolean Variable Names

Boolean variables should usually read naturally.

Good:

```go
isActive := true
isLoggedIn := false
hasPermission := true
canEdit := false
```

Then:

```go
if isActive {
    ...
}
```

reads naturally.

---

# 45. Avoid Redundant Names

Bad:

```go
userNameString := "Keshav"
```

If it's already obvious that `userName` is a string, don't encode the type into the variable name.

Better:

```go
userName := "Keshav"
```

The type belongs in the type system, not unnecessarily in the variable name.

---

# 46. Variable Declaration at the Right Time

Avoid declaring variables much earlier than needed.

Less focused:

```go
var name string
var age int
var score int

// hundreds of lines

name = "Keshav"
age = 19
score = 90
```

Better:

```go
name := "Keshav"
age := 19
score := 90
```

Keep declarations close to where the value becomes relevant.

This improves readability.

---

# 47. Don't Declare What You Don't Need

Bad:

```go
name := "Keshav"
age := 19
score := 90
unusedValue := 100

fmt.Println(name)
fmt.Println(age)
```

The unused variable causes a compiler error for local variables.

Go intentionally makes unused local variables a problem.

Why?

Because unused variables often indicate:

- unfinished code
- mistakes
- dead logic
- forgotten work

The compiler helps keep the code clean.

---

# 48. Unused Variables

This:

```go
func main() {
    age := 19
}
```

can produce a compiler error because `age` is declared but never used.

Go is strict about this.

That's intentional.

The language wants you to avoid meaningless local state.

---

# 49. The Blank Identifier `_`

Go provides `_` when you intentionally want to ignore a value.

For example:

```go
_, ok := something()
```

The `_` means:

> I don't need this value.

Important:

`_` is not a normal variable that stores something you can retrieve later.

It's the **blank identifier**.

---

# 50. Constants

Not every named value should be a variable.

If a value should never change:

```go
const maxRetries = 3
```

Then:

```go
maxRetries = 5
```

is invalid.

A constant represents a value that is fixed.

---

# 51. Variable vs Constant

Variable:

```go
age := 19

age = 20
```

Value can change.

Constant:

```go
const maxUsers = 100
```

Value cannot be reassigned.

Mental model:

```text
VARIABLE

name → value
        ↕
      changes


CONSTANT

name → fixed value
```

---

# 52. When Should You Use `const`?

Use a constant when the value conceptually does not change.

Examples:

```go
const maxUsers = 100
const appName = "MyApp"
const secondsPerMinute = 60
```

Don't make something a constant merely because you don't plan to change it today.

The question is:

> Is this value conceptually fixed?

---

# 53. Constants vs Magic Numbers

Instead of:

```go
if age >= 18 {
    ...
}
```

sometimes a named constant can improve clarity:

```go
const adultAge = 18

if age >= adultAge {
    ...
}
```

Whether this is better depends on context.

Don't create constants for every number in your code.

For example:

```go
const one = 1
const two = 2
```

would be ridiculous.

---

# 54. Variable Initialization

Initialization means giving the variable its initial value.

Example:

```go
age := 19
```

The initial value is:

```text
19
```

Another example:

```go
var age int = 19
```

Again:

```text
initial value → 19
```

---

# 55. Declaration Without Initialization

```go
var age int
```

This declares the variable but doesn't explicitly initialize it.

Go automatically gives it:

```text
zero value → 0
```

So:

```text
Declaration
    ↓
zero value
    ↓
can assign later
```

---

# 56. Reassignment Doesn't Redeclare

This:

```go
age := 19
age = 20
age = 21
```

has one variable:

```text
age
```

with changing values.

It does NOT create three variables.

```text
age → 19
age → 20
age → 21
```

---

# 57. Think About Variables as State

This is a powerful mental model.

A program's state can be thought of as:

```text
name      → "Keshav"
age       → 19
score     → 90
isActive  → true
```

As your program executes:

```text
age
 ↓
19
 ↓
20
 ↓
21
```

The variable represents a changing piece of state.

---

# 58. What Actually Happens in Memory?

Now let's go one level deeper.

Suppose:

```go
age := 19
```

At a conceptual level, the program needs storage for the value.

Think:

```text
Variable name
     │
     ▼
   age
     │
     ▼
┌──────────┐
│    19    │
└──────────┘
```

The exact physical memory representation is an implementation detail.

For learning Go, the important thing is:

> A variable gives a name to a value/storage that the program can access according to its type and scope.

Don't assume every variable is necessarily just a simplistic "box at a fixed memory address." Go's compiler and runtime are free to optimize how values are represented.

---

# 59. Compiler Optimization

Suppose:

```go
age := 19
fmt.Println(age)
```

The compiler can perform optimizations.

The actual generated machine code doesn't have to correspond literally to:

```text
allocate box
put 19
load box
print box
```

The compiler can optimize aggressively.

So use the **language-level mental model**:

```text
name → typed value
```

rather than trying to predict exact machine memory for every variable.

---

# 60. Variable Type Controls Operations

Suppose:

```go
age := 19
```

Go knows:

```text
age → int
```

So:

```go
age + 1
```

is valid.

But:

```go
age + "hello"
```

is invalid.

The type tells the compiler what operations are valid.

---

# 61. Explicit Type Conversion

Sometimes you have values of different numeric types.

For example:

```go
var age int = 19
var price float64 = 99.5
```

Go does not silently mix arbitrary numeric types.

You explicitly convert when appropriate:

```go
floatAge := float64(age)
```

Now:

```text
age      → int
floatAge → float64
```

This is called a **type conversion**.

---

# 62. Conversion Is Not Changing the Original Variable

Consider:

```go
age := 19

price := float64(age)
```

This doesn't turn `age` into a `float64`.

Instead:

```text
age
 ↓
19 (int)

price
 ↓
19 (float64)
```

They are separate variables.

---

# 63. Variable Declaration Style

Go gives you three common styles.

### 1. Short declaration

```go
age := 19
```

### 2. `var` with inferred type

```go
var age = 19
```

### 3. `var` with explicit type

```go
var age int = 19
```

All are valid.

---

# 64. Which One Should You Prefer?

For local variables, usually:

```go
age := 19
```

is the cleanest when the type is obvious.

Use:

```go
var age int
```

when you want to declare without an initial value.

Use:

```go
var age int = 19
```

when explicitly stating the type improves clarity or is otherwise useful.

Don't turn this into a rigid rule.

The goal is **clear code**.

---

# 65. Example: Good Use of `var`

```go
var total int

if condition {
    total = 100
} else {
    total = 200
}

fmt.Println(total)
```

Here the declaration-before-assignment structure makes sense.

---

# 66. Example: Good Use of `:=`

Instead of:

```go
var name string = "Keshav"
```

usually:

```go
name := "Keshav"
```

is simpler.

You're not losing useful information because `"Keshav"` clearly tells the reader the type is a string.

---

```text
┌───────────────────────────────┐
│        main scope             │
│                               │
│   name := "Keshav"            │
│                               │
│   ┌───────────────────────┐   │

│   cannot access age           │
│                               │
└───────────────────────────────┘
```

This is the scope mental model.

# 68. Shadowing Diagram

```text
┌─────────────────────────────┐
│ Outer scope                 │
│                             │
│ name → "Keshav"             │
│                             │
│   ┌─────────────────────┐   │
│   │ Inner scope         │   │
│   │                     │   │
│   │ name → "Rahul"      │   │
│   │                     │   │
│   └─────────────────────┘   │
│                             │
│ name → "Keshav"             │
└─────────────────────────────┘
```

The inner variable temporarily hides the outer variable.

---

# 69. Production Rule: Avoid Accidental Shadowing

Be careful with:

```go
value := 10

if condition {
    value := 20
    fmt.Println(value)
}

fmt.Println(value)
```

If your intention was to modify the outer `value`, use:

```go
value = 20
```

not:

```go
value := 20
```

This is one of those tiny mistakes that can cause confusing bugs.

---

# 70. Production Rule: Prefer Small Scope

Compare:

```go
var userAge int

// lots of code

userAge = 19
```

with:

```go
userAge := 19
```

The second version tells the reader immediately:

> This variable starts existing here.

Keeping variables close to their use makes code easier to reason about.

---

# 71. Production Rule: Don't Create "God Variables"

Avoid one variable carrying unrelated meanings.

Bad:

```go
data := 19
```

What is `data`?

Age?

Score?

Quantity?

ID?

Better:

```go
age := 19
```

Names are part of your program's design.

---

# 72. Production Rule: Don't Encode Types in Names

Avoid:

```go
userString := "Keshav"
ageInt := 19
activeBool := true
```

Prefer:

```go
userName := "Keshav"
age := 19
isActive := true
```

Go already has a type system.

---

# 73. Production Rule: Don't Over-Abbreviate

Bad:

```go
usrNm := "Keshav"
usrAg := 19
```

Better:

```go
userName := "Keshav"
userAge := 19
```

Shorter isn't automatically better.

Readable is better.

---

# 74. Production Rule: Use Constants for True Constants

Instead of scattering:

```go
60
60
60
60
```

if they all represent seconds per minute:

```go
const secondsPerMinute = 60
```

Now the meaning is explicit.

---

# 75. Production Rule: Don't Constant-ify Everything

This:

```go
const one = 1
const two = 2
const defaultName = "Keshav"
```

isn't automatically better.

Ask:

> Does giving this value a name improve understanding or maintainability?

If not, don't create another identifier.

---

# 76. Production Rule: Avoid Unnecessary Global Variables

This:

```go
var currentUser = "Keshav"
var score = 100
var count = 0
```

at package scope can make state accessible from many places.

That increases the number of places you need to reason about when something changes.

Prefer local variables when the data only belongs to a local operation.

---

# 77. Global vs Local Mental Model

Local:

```text
function
 └── variable
```

Easy to track.

Global/package-level:

```text
package
 ├── function A ──┐
 ├── function B ──┼── shared variable
 ├── function C ──┘
```

Now multiple pieces of code can potentially depend on the same state.

Use package-level variables deliberately.

---

# 78. Variable Lifetime

There's another useful concept:

**Lifetime** asks:

> How long does the variable/value need to exist?

For a local variable:

```go
func calculate() {
    result := 100
    fmt.Println(result)
}
```

you can conceptually think of `result` as relevant only to that function's execution.

The compiler may optimize its actual storage.

Again, don't assume:

```text
scope == exact physical memory lifetime
```

They are related concepts, but not identical.

---

# 79. Scope vs Lifetime

This distinction is worth remembering:

```text
Scope
→ where the name can be referenced in source code.

Lifetime
→ how long the associated value/storage needs to exist during execution.
```

Don't confuse the two.

---

# 80. Go Can Optimize Variable Storage

A common beginner mental model is:

```text
every variable → always lives on stack
```

or:

```text
every variable → always lives on heap
```

Don't think like that.

The Go compiler performs analysis and optimization.

For now, your useful model is:

```text
variable name
      ↓
typed value
      ↓
compiler/runtime manages representation
```

Later, when you study pointers and memory management, you can go much deeper into stack vs heap and escape analysis.

For now, don't mix those concepts into variable fundamentals.

---

# 81. Variable Initialization Order

Within normal sequential code, statements execute in order.

Example:

```go
age := 19

age = 20

fmt.Println(age)
```

The final value is:

```text
20
```

Think:

```text
age := 19
      ↓
age = 20
      ↓
print age
      ↓
20
```

---

# 82. Variables and Expressions

A variable can appear inside expressions.

```go
age := 19

nextAge := age + 1
```

Now:

```text
age     → 19
nextAge → 20
```

The expression:

```go
age + 1
```

produces a value.

That value is assigned to:

```go
nextAge
```

---

# 83. Variables Can Be Used to Build Other Variables

Example:

```go
price := 100
quantity := 3

total := price * quantity
```

Conceptually:

```text
price
 ↓
100

quantity
 ↓
3

price * quantity
 ↓
300

total
 ↓
300
```

This is how program state builds on previous state.

---

# 84. Variables Don't Automatically Stay Connected

This is important.

```go
age := 19
nextAge := age + 1
```

Now:

```text
age     → 19
nextAge → 20
```

If you later do:

```go
age = 30
```

`nextAge` does **not** automatically become `31`.

It remains:

```text
nextAge → 20
```

Why?

Because:

```go
nextAge := age + 1
```

evaluated the expression and assigned the resulting value.

It did not create a permanent formula.

---

# 85. Example

```go
age := 19
nextAge := age + 1

age = 30

fmt.Println(age)
fmt.Println(nextAge)
```

Output:

```text
30
20
```

This is a very important mental model.

---

# 86. Assignment Happens From the Right Side

Consider:

```go
age = age + 1
```

This can look weird mathematically.

But programming assignment isn't mathematical equality.

It means:

```text
read current age
      ↓
add 1
      ↓
store result back into age
```

If:

```text
age = 19
```

then:

```go
age = age + 1
```

becomes:

```text
19 + 1
 ↓
20
 ↓
age = 20
```

---

# 87. Variable Mutation

When you change:

```go
age = age + 1
```

you're **mutating the variable's value**.

The variable itself remains:

```text
age
```

Its current value changes:

```text
19 → 20
```

---

# 88. `var` With Zero Value

A very Go-like pattern:

```go
var count int

count++
count++
count++

fmt.Println(count)
```

Result:

```text
3
```

Why?

Initial state:

```text
count → 0
```

Then:

```text
0 → 1 → 2 → 3
```

Zero values make this pattern natural.

---

# 89. Variable Naming and Meaning

Compare:

```go
x := 19
```

with:

```go
userAge := 19
```

Both compile.

But:

```go
userAge := 19
```

communicates intent immediately.

Production code is read much more often than it is written.

So optimize names for the future reader.

# 99. Production-Grade Variable Checklist

Before creating a variable, ask:

```text
1. What does this value represent?
2. Does it need a name?
3. What type should it have?
4. Should I use := or var?
5. Should this value be a constant?
6. What scope does it actually need?
7. Am I declaring it too early?
8. Is the variable name meaningful?
9. Am I accidentally shadowing another variable?
10. Do I actually need this variable?
```

# 100. The Rules You Should Have in Muscle Memory

### Rule 1 — `:=` creates a variable

```go
age := 19
```

---

### Rule 2 — `=` changes an existing variable

```go
age = 20
```

---

### Rule 3 — Go is statically typed

```go
age := 19
```

means:

```text
age → int
```

You can't later assign a string to it.

---

### Rule 4 — `var` can declare without initialization

```go
var age int
```

gives:

```text
age → 0
```

---

### Rule 5 — Zero values are intentional

```text
int     → 0
string  → ""
bool    → false
```

---

### Rule 6 — Scope controls where a variable name is visible

```text
outer
 └── inner
```

Inner scopes can generally access appropriate outer variables.

---

### Rule 7 — `:=` can accidentally shadow

```go
name := "Keshav"

if true {
    name := "Rahul"
}
```

That's a new variable.

---

### Rule 8 — Assignment doesn't create a new variable

```go
name = "Rahul"
```

That's the existing variable.

---

### Rule 9 — Constants don't change

```go
const maxUsers = 100
```

---

### Rule 10 — Name variables by meaning

Prefer:

```go
userAge := 19
```

over:

```go
x := 19
```

when the context doesn't make `x` obvious.

---

# 101. Final Mental Model

Forget complicated definitions for a second.

When you see:

```go
age := 19
```

think:

```text
                PROGRAM STATE

                  age
                   │
                   ▼
             ┌───────────┐
             │    19     │
             └───────────┘
                   │
                   │
              type = int
```

Then:

```go
age = 20
```

means:

```text
                  age
                   │
                   ▼
             ┌───────────┐
             │    20     │
             └───────────┘
```

Not:

```text
new variable
```

but:

```text
same variable
new value
```

And:

```go
var age int
```

means:

```text
                  age
                   │
                   ▼
             ┌───────────┐
             │     0     │
             └───────────┘
```

because `0` is the zero value of `int`.

Finally, keep this distinction absolutely clear:

```text
┌──────────────────────────────────────┐
│                                      │
│  :=     → create + initialize        │
│                                      │
│  =      → assign/change value        │
│                                      │
│  var    → explicit declaration       │
│                                      │
│  const  → fixed value                │
│                                      │
│  scope  → where name is visible      │
│                                      │
│  type   → what kind of value it is   │
│                                      │
└──────────────────────────────────────┘
```
