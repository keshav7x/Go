# Go Slices — From First Principles to Production

<p><b>Goal:</b> By the end of this lesson, you should be able to look at a slice and understand what Go is actually doing underneath it, not just memorize syntax.</p>

---

# 1. First: Why Do Slices Exist?

Before understanding slices, remember what we learned about arrays.

An array has a **fixed size**.

```go
var numbers [5]int

numbers[0] = 10
numbers[1] = 20
numbers[2] = 30
numbers[3] = 40
numbers[4] = 50
```

The array has exactly 5 elements.

```text
[10] [20] [30] [40] [50]
```

But imagine you're building something like:

```text
Users
Messages
Products
Orders
Logs
Requests
```

You usually don't know beforehand exactly how many items you'll have.

Maybe:

```text
Today → 10 users
Tomorrow → 100 users
Next month → 10,000 users
```

A fixed array becomes inconvenient.

You could create:

```go
[100000]int
```

But now you've arbitrarily chosen a maximum.

What if you need 100001?

And what if you only need 10?

This is where **slices** come in.

---

# 2. What Is a Slice?

The simplest definition:

<p><b>A slice is a dynamic, flexible view over an array.</b></p>

That's the sentence you should remember.

A slice is **not itself an array**.

Instead, a slice describes:

```text
"Give me these elements from some underlying array."
```

Conceptually:

```text
Underlying array

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │ 70 │ 80 │
└────┴────┴────┴────┴────┴────┴────┴────┘
  ↑              ↑
  │              │
  └──── slice ───┘

slice:
10 20 30 40 50
```

The slice doesn't necessarily own those elements.

It refers to a region of an underlying array.

---

# 3. Array vs Slice

This distinction is extremely important.

```text
ARRAY

┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘

Size = fixed
```

Slice:

```text
SLICE

┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘
  ↑───────────────↑
       slice

Length can change
```

The underlying storage can also be replaced when the slice grows.

# 4. Creating a Slice

The most basic syntax:

```go
var numbers []int
```

Notice something important.

Array:

```go
var numbers [5]int
```

Slice:

```go
var numbers []int
```

There is **no number inside `[]`**.

That means:

```go
[5]int
```

is an array.

While:

```go
[]int
```

is a slice.

```text
numbers
```


# 6. But Here's Something Important

This:

```go

```

doesn't mean:

```text

```

Conceptually, it is a slice with:


We'll understand exactly what this means later.

For now:

```text

┌───────────────┐
│ pointer: nil  │
│ len: 0        │
│ cap: 0        │
└───────────────┘
```

This is called a **nil slice**.

# 14. Slice Boundaries


# 15. Why Slices Are Called "Dynamic"

Suppose:

```go
numbers := []int{10, 20, 30}
```

Initially:

```text
[10 20 30]
```

Now we want:

```text
[10 20 30 40]
```

We can use:

```go
numbers = append(numbers, 40)
```

Now:

```text
[10 20 30 40]
```

The slice grew.

This is one of the biggest differences between arrays and slices.

# 16. `append()`

`append()` is probably the most important slice operation.

```go
numbers := []int{10, 20, 30}

numbers = append(numbers, 40)
```

Result:

```text
[10 20 30 40]
```

Notice something VERY important:

```go
numbers = append(numbers, 40)
```

not:

```go
append(numbers, 40)
```

Why?

Because `append()` **returns a slice**.

The result must usually be assigned back.

---

# 17. Why Does `append()` Return a Slice?

This is where the internal behavior becomes interesting.

Suppose:

```go
numbers := []int{10, 20, 30}
```

Conceptually:

```text
slice

┌──────────────────────┐
│ pointer → array      │
│ len = 3              │
│ cap = 3              │
└──────────────────────┘

             ↓

        underlying array

        ┌────┬────┬────┐
        │ 10 │ 20 │ 30 │
        └────┴────┴────┘
```

Now:

```go
numbers = append(numbers, 40)
```

If there isn't enough capacity, Go needs a bigger underlying array.

Conceptually:

```text
OLD ARRAY

┌────┬────┬────┐
│ 10 │ 20 │ 30 │
└────┴────┴────┘

          ↓

       not enough room

          ↓

NEW ARRAY

┌────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │    │    │
└────┴────┴────┴────┴────┴────┘
```

The new slice now points to the new storage.

That's why `append()` returns a slice.

# 18. Slice Internals — The Big Mental Model

A slice is commonly represented conceptually by **three pieces of information**:

```text
┌────────────────────────────┐
│          SLICE             │
├────────────────────────────┤
│ pointer                    │
│ length                     │
│ capacity                   │
└────────────────────────────┘
```

Think:

```text
pointer
   ↓
"Where is the underlying data?"

length
   ↓
"How many elements can I currently access?"

capacity
   ↓
"How much underlying space is available before growth is needed?"
```

This mental model is incredibly important.

---

# 19. Length vs Capacity

Example:

```go
numbers := make([]int, 3, 5)
```

This creates:

```text
length = 3
capacity = 5
```

Think:

```text
Underlying storage

┌────┬────┬────┬────┬────┐
│ 0  │ 0  │ 0  │ ?  │ ?  │
└────┴────┴────┴────┴────┘
 ↑───────────────↑
      capacity

 ↑─────────↑
   length
```

The first 3 elements belong to the slice's current length.

The underlying storage has room for up to 5 elements before reallocation is needed.

---

# 20. `cap()`

You can inspect capacity using:

```go
cap(numbers)
```

Example:

```go
numbers := make([]int, 3, 5)

fmt.Println(len(numbers))
fmt.Println(cap(numbers))
```

Output:

```text
3
5
```

So:

```text
len = current usable elements
cap = available underlying capacity
```

---

# 21. `make()` With Capacity

Syntax:

```go
make([]T, length, capacity)
```

Example:

```go
numbers := make([]int, 3, 10)
```

Means:

```text
type     = int
length   = 3
capacity = 10
```

You can access:

```go
numbers[0]
numbers[1]
numbers[2]
```

But not:

```go
numbers[3]
```

Even though capacity is 10.

This is a VERY important distinction.

---

# 22. Capacity Does NOT Mean Length

This is wrong thinking:

```text
cap = 10
therefore indexes 0–9 are accessible
```

No.

If:

```go
numbers := make([]int, 3, 10)
```

Then:

```text
len = 3
cap = 10
```

Valid indexes:

```text
0
1
2
```

Not:

```text
3
4
5
...
9
```

Capacity is storage availability, not current slice length.

---

# 23. How `append()` Uses Capacity

Suppose:

```go
numbers := make([]int, 3, 5)
```

Current:

```text
len = 3
cap = 5
```

```text
┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │    │    │
└────┴────┴────┴────┴────┘
```

Now:

```go
numbers = append(numbers, 40)
```

There is capacity available.

So conceptually:

```text
┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │    │
└────┴────┴────┴────┴────┘

len = 4
cap = 5
```

Another append:

```go
numbers = append(numbers, 50)
```

Now:

```text
┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘

len = 5
cap = 5
```

Another:

```go
numbers = append(numbers, 60)
```

Now capacity is exhausted.

Go needs more storage.

Conceptually:

```text
OLD

┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘

              ↓

        allocate larger storage

              ↓

NEW

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┘
```

The exact capacity growth strategy is an implementation detail.

**Don't write production code assuming a specific growth factor.**

---

# 24. Why Reallocation Matters

Imagine:

```go
numbers := []int{}
```

Then:

```go
numbers = append(numbers, 1)
numbers = append(numbers, 2)
numbers = append(numbers, 3)
numbers = append(numbers, 4)
numbers = append(numbers, 5)
```

As the slice grows, Go may periodically allocate new backing storage and copy elements.

Conceptually:

```text
small storage
     ↓
bigger storage
     ↓
even bigger storage
     ↓
...
```

This is why repeatedly growing slices can involve allocations.

# 25. Preallocating a Slice

If you already know approximately how many elements you'll need:

```go
numbers := make([]int, 0, 100)
```

Now:

```text
len = 0
cap = 100
```

You can append:

```go
numbers = append(numbers, 10)
numbers = append(numbers, 20)
numbers = append(numbers, 30)
```

You haven't initially created 100 logical elements.

You've created:

```text
0 elements
100 capacity
```

This is useful when you expect the slice to grow to a known approximate size.

---

# 26. `make([]int, 100)` vs `make([]int, 0, 100)`

These are VERY different.

### First:

```go
numbers := make([]int, 100)
```

Means:

```text
len = 100
cap = 100
```

There are 100 elements.

### Second:

```go
numbers := make([]int, 0, 100)
```

Means:

```text
len = 0
cap = 100
```

There are zero elements, but storage has been reserved for growth.

Remember this distinction.


```text
6
```

# 29. `...` Here Is Not a New Data Structure

Don't overthink it.

This:

```go

```

means:

```text
take the elements inside b
and pass them individually
```

Example:

```go
numbers := []int{1, 2, 3}

numbers = append(numbers, 4, 5)
```

and:

```go
extra := []int{4, 5}

numbers = append(numbers, extra...)
```

produce the same logical result.

# 34. Important `range` Behavior

Look at this:

```go
numbers := []int{10, 20, 30}

for _, value := range numbers {
    value = value * 2
}

fmt.Println(numbers)
```

You might expect:

```text
[20 40 60]
```

But you'll get:

```text
[10 20 30]
```

Why?

Because `value` is a loop variable containing the element's value.

You're changing the variable:

```text
value
```

not the slice element.

# 35. Correct Way to Modify Elements


Result:

```text

```

Mental model:

```text
range gives you

index ─────────────→ actual element position
value ─────────────→ current value
```

If you need to modify the slice:

```text
use the index
```

# 36. Slicing a Slice

Now we reach one of the most important slice features.

Suppose:

```go
numbers := []int{10, 20, 30, 40, 50}
```

You can create another slice from it:

```go
part := numbers[1:4]
```

Result:

```text
[20 30 40]
```

Why?

The syntax:

```go
numbers[start:end]
```

means:

```text
start = included
end   = excluded
```

So:

```go
numbers[1:4]
```

means indexes:

```text
1
2
3
```

but NOT:

```text
4
```

---

```text
       ↑              ↑
       1              4
       │              │
       └──── [1:4] ───┘
```

Result:

```text
[20 30 40]
```

# 38. The Rule for Slicing

Memorize:

```text
[start:end]

start → included
end   → excluded
```

Examples:

```go

```

gives:

```text

```

```go
numbers[2:5]
```

gives:

```text

```

# 41. Copying a Slice Variable Is Not Copying Its Elements

This is a very important concept.

Suppose:

```go
a := []int{10, 20, 30}
b := a
```

You might think:

```text
a → [10 20 30]

b → [10 20 30]
```

as two completely independent arrays.

That's not necessarily what happens.

Conceptually:

```text
a ─────┐
       │
       ↓
   underlying array
   ┌────┬────┬────┐
   │ 10 │ 20 │ 30 │
   └────┴────┴────┘
       ↑
       │
b ─────┘
```

Both slices can refer to the same underlying storage.

---

# 42. Example

```go
a := []int{10, 20, 30}
b := a

b[0] = 999

fmt.Println(a)
fmt.Println(b)
```

Result:

```text
[999 20 30]
[999 20 30]
```

Why?

Because `a` and `b` refer to the same underlying elements in this case.

This is one of the biggest differences from assigning an array.

---

# 43. Arrays vs Slices When Assigning

Array:

```go
a := [3]int{10, 20, 30}
b := a

b[0] = 999
```

Now:

```text
a = [10 20 30]
b = [999 20 30]
```

The array was copied.

Slice:

```go
a := []int{10, 20, 30}
b := a

b[0] = 999
```

Now both can observe:

```text
a = [999 20 30]
b = [999 20 30]
```

because the slice refers to underlying storage.

---

# 44. Why This Matters

This becomes extremely important when passing slices around.

If two slices refer to the same underlying elements:

```text
slice A ──┐
          ↓
       [10 20 30 40]
          ↑
slice B ──┘
```

changing an element through one can be visible through the other.

So you should always ask:

> "Are these slices sharing underlying storage?"

That's a very important Go mental model.

# 45. `copy()`

Go provides the `copy()` function when you want to copy elements between slices.

Example:

```go
source := []int{10, 20, 30}
destination := make([]int, 3)

copy(destination, source)
```

Now:

```text
source
[10 20 30]

destination
[10 20 30]
```

The elements were copied.

---

# 46. `copy()` Syntax

```go
copy(destination, source)
```

Example:

```go
copy(destination, source)
```

Think:

```text
source
   ↓
[10 20 30]

        copy

          ↓

destination
[10 20 30]
```

---

# 47. `copy()` Does Not Require Equal Lengths

Suppose:

```go
source := []int{10, 20, 30, 40, 50}

destination := make([]int, 2)

copy(destination, source)
```

Result:

```text
destination = [10 20]
```

Only as many elements as fit are copied.

The number copied is:

```text
minimum(destination length, source length)
```

So:

```text
min(2, 5) = 2
```

---

# 48. `copy()` Returns a Number

You can do:

```go
copied := copy(destination, source)

fmt.Println(copied)
```

It returns the number of elements copied.

# 53. Removing an Element

Go does **not** have a dedicated:

```go
remove()
```

method for slices.

You usually build the desired slice using slicing and `append()`.

Suppose:

```go
numbers := []int{10, 20, 30, 40, 50}
```

We want to remove:

```text
30
```

index:

```text
2
```

One common technique is:

```go
numbers = append(numbers[:2], numbers[3:]...)
```

Result:

```text
[10 20 40 50]
```

Let's understand it.

First:

```go
numbers[:2]
```

gives:

```text
[10 20]
```

Second:

```go
numbers[3:]
```

gives:

```text
[40 50]
```

Then:

```go
append([10 20], [40 50]...)
```

produces:

```text
[10 20 40 50]
```

# 56. Important: Slicing Does Not Automatically Copy

This:

```go
part := numbers[1:4]
```

usually creates another slice referring to the same underlying elements.

Conceptually:

```text
original

┌────┬────┬────┬────┬────┐
│ 10 │ 20 │ 30 │ 40 │ 50 │
└────┴────┴────┴────┴────┘
       ↑───────────↑
       part
```

So:

```go
part[0] = 999
```

can change:

```text
numbers
```

as well.

---

# 57. Example

```go
numbers := []int{10, 20, 30, 40, 50}

part := numbers[1:4]

part[0] = 999

fmt.Println(numbers)
fmt.Println(part)
```

Result:

```text
[10 999 30 40 50]
[999 30 40]
```

This is because both slices refer to the same underlying data.

# 58. If You Want an Independent Copy

Use `copy()`.

```go
numbers := []int{10, 20, 30, 40, 50}

part := make([]int, 3)

copy(part, numbers[1:4])
```

Now:

```text
numbers
[10 20 30 40 50]

part
[20 30 40]
```

They have separate storage.

Then:

```go
part[0] = 999
```

doesn't change:

```text
numbers
```

# 59. Three-Index Slice

Go also supports:

```go
slice[low:high:max]
```

Example:

```go
numbers := []int{10, 20, 30, 40, 50}

part := numbers[1:3:3]
```

Now:

```text
len(part) = 2
cap(part) = 2
```

This controls the capacity of the resulting slice.

You don't need to use this every day, but understanding why it exists is useful.

It can prevent the resulting slice from sharing extra capacity with the original slice.

# 60. Why Would You Limit Capacity?

Suppose:

```go
numbers := []int{10, 20, 30, 40, 50}
```

and:

```go
part := numbers[1:3]
```

`part` contains:

```text
[20 30]
```

but its underlying storage may still have access to later elements.

Using:

```go
part := numbers[1:3:3]
```

limits its capacity.

Think:

```text
numbers

[10 20 30 40 50]
     ↑────↑
     part

part length = 2
part capacity = 2
```

This becomes useful when you want to control what later `append()` operations can reuse.

---

# 61. Slice Capacity After Slicing

Suppose:

```go
numbers := []int{10, 20, 30, 40, 50}
```

Then:

```go
part := numbers[1:3]
```

The resulting slice has:

```text
len = 2
```

Its capacity extends from index 1 toward the end of the underlying array.

Conceptually:

```text
[10 20 30 40 50]
    ↑──────────────
    capacity region
```

So:

```text
len(part) = 2
cap(part) = 4
```

The important idea is:

<p><b>Capacity depends on where the slice starts inside its underlying array.</b></p>

# 62. `append()` Can Change What Another Slice Sees

This is one of the trickiest slice behaviors.

Suppose:

```go
a := make([]int, 2, 4)

a[0] = 10
a[1] = 20

b := a
```

Now:

```text
a
[10 20]

b
[10 20]

shared underlying storage
```

Then:

```go
a = append(a, 30)
```

There may still be capacity available.

So `a` may reuse the same underlying storage.

Now:

```text
underlying storage

[10 20 30 _]
 ↑
 a
 ↑
 b
```

But:

```text
a len = 3
b len = 2
```

`b` doesn't automatically grow its length.

This is why slice behavior can seem weird until you understand:

```text
slice header
+
underlying array
```

# 63. The Slice Is Not the Data

This is probably the most important internal mental model.

Don't imagine:

```text
slice = array
```

Instead imagine:

```text
slice

┌─────────────┐
│ pointer     │ ───────────┐
│ len         │            │
│ cap         │            ↓
└─────────────┘      underlying array
                     ┌────┬────┬────┬────┐
                     │ 10 │ 20 │ 30 │ 40 │
                     └────┴────┴────┴────┘
```

The slice is a small descriptor.

The actual elements live in underlying storage.

# 64. Why Is This Design Useful?

Because slices can be cheap to pass around.

Instead of copying a potentially huge array every time, a slice can describe a region of existing storage.

Conceptually:

```text
large data

┌────────────────────────────────────┐
│ many elements                      │
└────────────────────────────────────┘
       ↑
       │
small slice descriptor
```

That's a major reason slices are so fundamental in Go.

# 65. Slice Is a Descriptor

For learning purposes, think of a slice as:

```text
├──────────────┤

├──────────────┤

└──────────────┘
```

# 66. What Happens During `append()` Internally?

```text
          │
          ↓

                 ↓

                 ↓

                 ↓
```

This is the mental model you should have.

# 80. Common Beginner Mistake

This:

```go
numbers := make([]int, 0, 5)

numbers[0] = 10
```

is WRONG.

Why?

Because:

```text
len = 0
```

There are no accessible elements.

Capacity is 5, but length is 0.

Correct:

```go
numbers = append(numbers, 10)
```

Now:

```text
len = 1
```

and:

```go
numbers[0] = 10
```

is valid.

---

# 81. Another Common Mistake

This:

```go
numbers := make([]int, 5)

numbers = append(numbers, 10)
```

is valid.

But now you have:

```text
[0 0 0 0 0 10]
```

You did NOT create:

```text
[10 0 0 0 0]
```

Why?

Because the original slice already had five elements.

Appending adds another element after them.

# 82. Choosing `make()` Correctly

If you want actual elements:

```go
numbers := make([]int, 5)
```

If you want an empty slice that you plan to grow:

```go
numbers := make([]int, 0, 5)
```

Mental distinction:

```text
make([]int, 5)

"Give me 5 elements."
```

vs:

```text
make([]int, 0, 5)

"Give me 0 elements, but prepare room for growth."
```

# 83. Production Practice: Preallocate When Size Is Known

Suppose you know you'll collect approximately 1000 values.

Instead of:

```go
numbers := []int{}

for i := 0; i < 1000; i++ {
    numbers = append(numbers, i)
}
```

you can use:

```go
numbers := make([]int, 0, 1000)

for i := 0; i < 1000; i++ {
    numbers = append(numbers, i)
}
```

This can reduce reallocations.

But don't blindly preallocate huge capacities without reason.

First write correct code.

# 86. Production Practice: Be Careful With Shared Backing Arrays

This is one of the most important real-world slice bugs.

You might have:

```go
data := []int{1, 2, 3, 4, 5}

part := data[:2]
```

Now:

```text
data
[1 2 3 4 5]

part
[1 2]
```

They share storage.

If you don't want that relationship, explicitly copy:

```go
part := make([]int, 2)
copy(part, data[:2])
```

The key question is:

> "Should this new slice share the original data or own an independent copy?"

Know the answer before choosing the operation.

---

# 87. Production Practice: Don't Retain Huge Data Accidentally

Imagine:

```text
huge slice
[ millions of elements ]
```

You take a tiny slice:

```go
small := huge[0:5]
```

`small` can still refer to the underlying storage associated with the larger data.

This means keeping `small` around can keep that backing storage relevant.

If you truly need only those five values independently, make a copy.

Conceptually:

```text
Huge storage
████████████████████████████████

small
█████
 ↑
still references huge storage
```

versus:

```text
Huge storage
████████████████████████████████

small copy
█████
 ↑
independent small storage
```

This is an important memory-management consideration.

---

# 88. Production Practice: Don't Assume `append()` Preserves Sharing

This is subtle.

Before:

```text
a ──→ underlying array
b ──→ same underlying array
```

After:

```go
a = append(a, value)
```

if capacity isn't sufficient, Go can allocate new storage.

Now:

```text
a ──→ NEW array

b ──→ OLD array
```

So whether two slices continue sharing storage can change after `append()`.

Don't build fragile code around assumptions about the backing array.

---

# 89. Production Practice: Understand Ownership

Whenever you work with slices, mentally ask:

```text
Who owns these elements?

Who can modify them?

Are they shared?

Does this function need to modify them?

Should I copy them?
```

You don't need a formal ownership system in Go.

But thinking this way prevents many bugs.

```text

3. A slice has:

   - length
   - capacity

4. len() tells current element count.

5. cap() tells available backing capacity from the slice's start.

6. Indexing is limited by len(), not cap().

7. append() grows a slice.

8. append() may reuse storage or allocate new storage.

9. Always use:
   s = append(s, value)

10. Slicing normally does not copy elements.

11. Multiple slices can share the same underlying storage.

12. copy() creates independent element copies.

13. range gives you an index and a value.

14. Modifying the range value does not modify the slice.

15. Use the index when modifying slice elements.

16. make([]T, n) creates n elements.

17. make([]T, 0, n) creates 0 elements with capacity n.

18. Never confuse length with capacity.

19. Don't depend on Go's exact capacity-growth algorithm.

20. Before copying/slicing/returning data, think about
    whether sharing the underlying storage is intended.
```
