# Go Control Flow — `if`, `else`, and `switch`

> **Level:** Beginner → Intermediate → Production
>
> **Goal:** Understand control flow from first principles, not just memorize syntax.

## 1. What Is Control Flow?

<p>
A program normally executes from top to bottom.
</p>

```go
package main

import "fmt"

func main() {
    fmt.Println("A")
    fmt.Println("B")
    fmt.Println("C")
}
```

Execution:

```text
A
 ↓
B
 ↓
C
```

But real programs need to make decisions.

```text
                 Program
                    |
              ┌─────┴─────┐
              ↓           ↓
            true         false
              |             |
              ↓             ↓
          do this       do that
```

<p>
This is called <strong>control flow</strong>.
</p>

---

## 2. `if` — Making a Decision

### The basic idea

An `if` statement asks a question.

```go
if condition {
    // code runs when condition is true
}
```

For example:

```go
package main

import "fmt"

func main() {
    age := 20

    if age >= 18 {
        fmt.Println("You are an adult")
    }
}
```

The important part is:

```go
age >= 18
```

This expression produces a boolean:

```text
age >= 18
     |
     v
  ┌───────┐
  │ true  │
  └───┬───┘
      |
      v
 execute block
```

If the condition is false:

```text
age >= 18
     |
     v
  ┌────────┐
  │ false  │
  └───┬────┘
      |
      v
 skip block
```

---

## 3. Why Go Requires `bool`

Go does not automatically convert values into booleans.

This is invalid:

```go
age := 20

if age {
    fmt.Println("adult")
}
```

Go requires an actual boolean expression:

```go
if age >= 18 {
    fmt.Println("adult")
}
```

This is part of Go's philosophy:

> **Be explicit.**

---

## 4. `if` + `else`

When there are exactly two possible paths:

```go
if age >= 18 {
    fmt.Println("adult")
} else {
    fmt.Println("minor")
}
```

Think of it as:

```text
                 age >= 18?
                  /      \
                yes       no
                 |         |
                 v         v
              adult      minor
```

---

## 5. `else if`

When there are multiple conditions:

```go
if age < 13 {
    fmt.Println("child")
} else if age < 18 {
    fmt.Println("teenager")
} else {
    fmt.Println("adult")
}
```

Go evaluates from top to bottom.

```text
age < 13?
   |
   ├── yes → child
   |
   └── no
        |
        v
    age < 18?
        |
        ├── yes → teenager
        |
        └── no → adult
```

### Important

The order matters.

This is wrong:

```go
if age >= 18 {
    fmt.Println("adult")
} else if age >= 60 {
    fmt.Println("senior")
}
```

A person who is 70 satisfies:

```text
70 >= 18 → true
```

So the `senior` branch is never reached.

Correct:

```go
if age >= 60 {
    fmt.Println("senior")
} else if age >= 18 {
    fmt.Println("adult")
}
```

---

## 6. Production Pattern: Guard Clauses

Avoid deeply nested code.

### ❌ Hard to read

```go
func processUser(user *User) {
    if user != nil {
        if user.Active {
            if user.Verified {
                process(user)
            }
        }
    }
}
```

The actual business logic is buried.

### ✅ Idiomatic Go

```go
func processUser(user *User) {
    if user == nil {
        return
    }

    if !user.Active {
        return
    }

    if !user.Verified {
        return
    }

    process(user)
}
```

Think:

```text
               processUser
                    |
              user exists?
               /        \
             no          yes
             |            |
           return      user active?
                         /       \
                       no         yes
                       |           |
                     return    user verified?
                                  /       \
                                no         yes
                                |           |
                              return     process()
```

<p>
This pattern is called a <strong>guard clause</strong> or <strong>early return</strong>.
</p>

---

## 7. Why Early Returns Are Good

Compare:

```go
if valid {
    if authorized {
        if exists {
            process()
        }
    }
}
```

with:

```go
if !valid {
    return
}

if !authorized {
    return
}

if !exists {
    return
}

process()
```

The second version makes the happy path obvious:

```text
validate
   ↓
authorize
   ↓
check prerequisites
   ↓
process
```

This pattern appears constantly in production Go:

- HTTP handlers
- authentication
- authorization
- validation
- services
- repositories
- database operations

## 8. `switch`

Use `switch` when you have multiple discrete possibilities.

```go
switch method {
case "GET":
    fmt.Println("read")

case "POST":
    fmt.Println("create")

case "PUT":
    fmt.Println("update")

case "DELETE":
    fmt.Println("delete")

default:
    fmt.Println("unsupported method")
}
```

Conceptually:

```text
                 method
                   |
       ┌───────────┼───────────┐
       ↓           ↓           ↓
      GET         POST        DELETE
       |           |           |
       v           v           v
     read        create      delete
```

---

## 9. Go `switch` Does Not Need `break`

In many languages you might write:

```text
case 200:
    ...
    break
```

Go automatically exits the matching case.

```go
switch status {
case 200:
    fmt.Println("success")

case 404:
    fmt.Println("not found")

default:
    fmt.Println("unknown")
}
```

If `status == 200`:

```text
200
 |
 v
case 200
 |
 v
"success"
 |
 v
exit switch
```

No explicit `break` is necessary.

---

## 10. Multiple Values in a Case

You can group cases:

```go
switch method {
case "GET", "HEAD":
    fmt.Println("read operation")

case "POST":
    fmt.Println("create operation")

default:
    fmt.Println("other operation")
}
```

This is useful when multiple values have exactly the same behavior.

---

## 11. Expressionless `switch`

Go allows:

```go
switch {
case age < 13:
    fmt.Println("child")

case age < 18:
    fmt.Println("teenager")

case age < 60:
    fmt.Println("adult")

default:
    fmt.Println("senior")
}
```

This is essentially a clean decision tree.

```text
age < 13?
   |
   ├── yes → child
   |
   └── no
        |
        v
     age < 18?
        |
        ├── yes → teenager
        |
        └── no
             |
             v
          age < 60?
             |
             ├── yes → adult
             |
             └── no → senior
```

## 12. `if` vs `switch`

A useful mental model:

| Situation | Prefer |
|---|---|
| Check a condition | `if` |
| Guard clause | `if` |
| Two possible paths | `if / else` |
| Many discrete values | `switch` |
| HTTP methods | `switch` |
| Status values | `switch` |
| User roles | `switch` |
| Complex boolean condition | `if` |
| Range-based conditions | `if` or expressionless `switch` |

Don't blindly follow the table.

The real question is:

> **Which construct makes the intent easiest to understand?**

## 13. Short-Circuit Evaluation

Consider:

```go
if user != nil && user.Active {
    process(user)
}
```

Go evaluates from left to right.

If:

```go
user != nil
```

is false, Go doesn't evaluate:

```go
user.Active
```

because the whole expression is already false.

```text
user != nil?
     |
     ├── false → STOP
     |
     └── true
          |
          v
      user.Active?
```

This is called **short-circuit evaluation**.

---

## 14. `&&`, `||`, and `!`

### AND

```go
if user.Active && user.Verified {
    allow()
}
```

Both conditions must be true.

### OR

```go
if role == "admin" || role == "moderator" {
    allow()
}
```

At least one must be true.

### NOT

```go
if !user.Active {
    return
}
```

Means:

```text
user.Active == false
```

## 15. Scoped `if` Variables

Go allows initialization directly inside an `if`:

```go
if age := getAge(); age >= 18 {
    fmt.Println(age)
}
```

The structure is:

```text
initialization
      |
      v
age := getAge()
      |
      v
condition
      |
      v
age >= 18
```

The variable only exists within the `if` statement.

This:

```go
if age := getAge(); age >= 18 {
    fmt.Println(age)
}
```

is valid.

This is not:

```go
fmt.Println(age)
```

because `age` is out of scope.

---

## 16. Why This Is Common in Go

You'll frequently see:

```go
if err := doSomething(); err != nil {
    return err
}
```

This is one of the most recognizable Go patterns.

The error only needs to exist for the check, so keeping it scoped is clean.

# Production Patterns

## 17. HTTP Status Handling

```go
func handleStatus(status int) error {
    switch status {
    case 200, 201, 204:
        return nil

    case 400:
        return ErrBadRequest

    case 401:
        return ErrUnauthorized

    case 403:
        return ErrForbidden

    case 404:
        return ErrNotFound

    case 429:
        return ErrRateLimited

    default:
        return ErrUnexpectedStatus
    }
}
```

This is much clearer than:

```go
if status == 200 {
    ...
} else if status == 201 {
    ...
} else if status == 204 {
    ...
} else if status == 400 {
    ...
}
```

---

## 18. Validation

A production-style validation function might look like:

```go
func validateCreateUser(req CreateUserRequest) error {
    if req.Email == "" {
        return errors.New("email is required")
    }

    if req.Password == "" {
        return errors.New("password is required")
    }

    if len(req.Password) < 8 {
        return errors.New("password must contain at least 8 characters")
    }

    return nil
}
```

Notice:

```text
invalid
   ↓
return error

invalid
   ↓
return error

invalid
   ↓
return error

everything valid
   ↓
nil
```

---

## 19. Avoid Boolean Soup

This is technically valid:

```go
if user.Active &&
    user.Verified &&
    !user.Suspended &&
    user.Role != "guest" &&
    user.Email != "" {
    process(user)
}
```

But as business rules grow, it becomes difficult to understand.

Consider:

```go
eligible := user.Active &&
    user.Verified &&
    !user.Suspended

if !eligible {
    return ErrNotEligible
}

if user.Role == "guest" {
    return ErrForbidden
}

if user.Email == "" {
    return ErrInvalidUser
}

process(user)
```

Or encapsulate the rule:

```go
if canAccessDashboard(user) {
    showDashboard()
}
```

The best choice depends on context.

# Production Checklist

Before committing code containing `if` or `switch`, ask:

```text
□ Is the condition easy to understand?

□ Is there unnecessary nesting?

□ Can I use a guard clause?

□ Are the conditions ordered correctly?

□ Could an earlier condition swallow a later one?

□ Are temporary variables scoped appropriately?

□ Am I ignoring an error?

□ Does the condition perform I/O?

□ Does the condition have side effects?

□ Would a switch communicate the intent better?

□ Are magic strings/numbers hiding domain meaning?

□ Is the happy path obvious?

□ Can another engineer debug this quickly?
```

# The Mental Model

Don't memorize:

```go
if
else
switch
```

Memorize the underlying ideas:

```text
                 CONTROL FLOW
                      |
          ┌───────────┼───────────┐
          |           |           |
          v           v           v
         IF         SWITCH       FOR
          |           |
          |           |
      decision    selection
          |           |
          v           v
      condition     cases
```

For `if`:

```text
condition
    |
    v
 bool?
 /   \
yes   no
 |     |
 v     v
run   skip
```

For `switch`:

```text
value / condition
        |
        v
   match a case
    /    |    \
   A     B   default
   |     |      |
   v     v      v
 work  work   fallback
```

For production Go:

```text
validate
   ↓
guard
   ↓
authorize
   ↓
execute
   ↓
return
```

# Final Challenge

Build:

```go
func processRequest(
    user *User,
    method string,
    status int,
) error
```

Requirements:

```text
1. User must exist
2. User must be active
3. GET / POST / DELETE must be handled
4. Unsupported methods must return an error
5. 2xx = success
6. 4xx = client error
7. 5xx = server error
8. Use guard clauses
9. Use switch where appropriate
10. Avoid unnecessary nesting
11. Don't ignore errors
12. Keep the happy path readable
```

Your final control flow should roughly communicate:

```text
                  request
                     |
                     v
               user exists?
                /        \
              no          yes
              |            |
            error      user active?
                          /      \
                        no        yes
                        |          |
```
